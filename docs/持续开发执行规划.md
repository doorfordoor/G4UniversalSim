## 1. 使用规则

### 1.1 事实来源优先级

发生冲突时按以下顺序判断：

1. `src/`、`include/`、`main.cc`、配置解析器和真实运行测试。
2. 当前 Git 提交、工作区 diff 和测试结果。
3. `docs/功能支持矩阵.md` 中经过代码核对的支持等级。
4. 本文和其他路线、交接、说明文档。

GUI 控件、配置字段名、类名、空接口、预览模型或文档中的“已完成”均不能单独证明功能已经支持。

几何模式的产品分类、显示名、兼容和剪枝规则见 `docs/几何模式与界面命名规范.md`。后端模板 token 与 GUI 显示名必须分离，不能为了界面易读而改写既有接口。

### 1.2 状态口径

| 状态 | 含义 |
| --- | --- |
| 已提交 | 实现已进入当前 Git 历史，并能给出提交号。 |
| 工作区待复审 | 实现存在于未提交工作区，尚不能作为 Git 基线。 |
| 已验证 | 已使用与当前源码对应的构建产物运行规定测试。 |
| 部分验证 | 只通过静态、解析、GUI smoke 或有限后端测试，仍有未验证层级。 |
| 受阻 | 存在明确缺陷、环境缺失或外部依赖，尚未达到提交门槛。 |
| 仅规划 | 尚未实现，不得写入“支持”列表。 |

每个阶段必须分别报告“已实现、已验证、已提交、已推送、仅规划”，不得把这些状态合并为一个“完成”。

### 1.3 当前受保护工作区

规划快照基线：

- 分支：`codex`。
- HEAD：`018345c fix(geometry): report source-aware config warnings`。
- `.gitignore` 是用户已有的唯一 staged 文件，index blob 必须保持为 `2c469d42c51c97f60baf22d61ef8ca3bad9a8752`。
- `总体判断.md` 是未跟踪用户文件，不得修改或提交。
- `docs/当前开发交接.md` 是现场交接快照；它不替代本文，也不得在未确认来源和提交边界时混入功能提交。
- 禁止 `git add -A`、`git reset --hard`、`git checkout --` 和未经授权的提交、推送。

如果 HEAD、staged 文件或保护项发生变化，所有执行 Agent 必须先停止写入，重新审计并更新本文的当前队列。

## 2. 总体产品目标

G4UniversalSim 的长期目标是成为配置驱动、可复现、可验证并且容易使用和扩展的 Geant4 桌面工作台。CLI、macro、GUI 和未来扩展入口必须收敛到同一套后端事实、有效配置、运行生命周期和输出契约。

总体路线分为：

| 阶段 | 核心目标 | 进入下一阶段的必要条件 |
| --- | --- | --- |
| M0 | 可信运行基础 | 能证明最终运行了什么、为什么成功或失败、产生了什么输出。 |
| M1 | Geant4 后端能力 | 新能力具备解析、校验、运行时、生命周期和后端测试闭环。 |
| M2 | 物理计分和验证 | 物理量定义、单位、权重、统计、MT 合并和基准全部明确。 |
| M3 | GUI 产品化 | GUI 由后端能力驱动，完整保护 round-trip，并提供可靠运行和诊断体验。 |
| M4 | 测试、发布和生态 | CI、安装包、迁移、兼容矩阵、性能、示例和发布流程稳定。 |
| M5 | 可扩展平台 | 能通过受控接口增加几何、构建模式、源、物理、计分和输出能力。 |

主执行顺序固定为：

`B2B2 复审提交 → GUI 演示改动整理 → M0-3C → M0-3D/E → M0-3B3 → M0-4/5 → M1 → M2 → M3 完整闭环 → M4 → M5`

除非用户明确调整优先级，不得因为 GUI 展示需求跳过 M0 的运行真实性，也不得在 M2 物理验证前开放未验证 scorer。

## 3. 所有工作包的统一完成门槛

每个新增或修改功能都必须逐项检查：

1. 配置解析：INI、macro、CLI 或其他入口是否真正读取，路径和单位如何解析。
2. 配置校验：缺失、非法、冲突、依赖和未知字段如何报告。
3. 运行时实现：Geant4 对象、生命周期、线程模型和失败路径是否真实执行。
4. GUI：只生成后端已实现子集；预览、实验和不可用状态必须明确。
5. 输出：生成条件、字段、单位、量纲、线程后缀、合并和未生成原因是否定义。
6. 测试：解析、GUI、后端、MT 和必要物理基准是否覆盖。
7. 文档：中文人类文档、Agent 规则、支持矩阵和示例是否同步。
8. 兼容：接口改名、默认值变化、schema 变化是否提供迁移策略。

仅增加配置字段、枚举、按钮、预览、空类或 stub 不算完成。不能完成完整链路时，状态必须保留为“部分支持”或“未支持”。

## 6. M1：Geant4 后端能力

M1 只扩展真实后端能力。每项能力必须先在 C++ 层闭环，再允许 GUI writer 开放。

### 6.1 M1-0：后端能力清单和 schema 基础

- 建立机器可读的能力清单，包含模板、solid、placement、材料、源、物理、计分和输出版本。
- 每项能力标记解析、校验、运行、输出和验证等级。
- GUI 只能消费该清单，不得维护更宽松的独立支持白名单。

### 6.2 M1-1：原生 solid 扩展

- 不采用一个无类型参数数组长期承载全部复杂 solid；优先设计可版本化的 shape-specific 字段。

### 6.3 M1-2：placement 模式

- 实现 `replica`、`parameterised`、`assembly` 的真实 Geant4 构建路径。
- 定义父子关系、copy number、轴、数量、间距、参数化回调和敏感体行为。
- 验证 MT、overlap、region、sensitive、bias 和 reinitialize 生命周期。

### 6.4 M1-3：GDML 和外部几何

- 实现真实 GDML 加载、world 选择、材料冲突、路径解析和错误回指。

- CAD/STL 作为独立工作包评估，不得因 GDML 完成自动宣称支持。
- 加入最小、嵌套、无效、外部引用和跨平台路径测试。

### 6.5 M1-4：材料能力

- 明确 `temperature`、`pressure`、`state` 与 G4Material 构造语义。
- 增加光学属性前先定义单位、插值、能量顺序和数据文件格式。
- 继续验证 isotope、element、mass fraction、atom count、volume fraction 的依赖和循环错误。
- 材料 schema 升级必须提供版本和迁移。

### 6.6 M1-5：region、cuts、sensitive 和 bias 生命周期

- 统一 geometry `cut.*` 与 `[physics.region.*]` 的唯一语义。
- 固化 region 创建、root logical volume、production cuts 和重建行为。
- 验证 sensitive detector、scorer、bias operator 和 geometry registry 在 reinitialize 后不重复、不丢失。

### 6.7 M1-6：重建与运行生命周期

M1 完成门槛：新增能力有真实 Geant4 对象和生命周期证据，不存在“字段能解析但运行时忽略”的灰色入口。

## 7. M2：物理计分和验证

M2 的顺序是先定义物理量和数据契约，再编码 scorer，最后开放 GUI。

### 7.1 M2-0：统一计分定义

- 为每个 scorer 编写物理定义、统计对象、单位、权重、归一化和误差含义。
- 明确 step、track、event、run 和 volume 聚合层级。
- 明确 ST/MT 合并、随机种子和可重复性边界。

### 7.2 M2-1：LET

- 选择并记录 LET 定义，例如 track-averaged 或 dose-averaged。
- 定义能量损失、步长、密度、材料和二次粒子处理。
- 建立解析参考或可信 benchmark，并覆盖零步长和边界情况。

### 7.3 M2-2：Dose

- 定义质量来源、复合体积、材料密度和动态几何变化下的处理。
- 处理零质量、无沉积、权重事件和统计不确定度。
- 输出使用明确剂量单位和 schema。

### 7.4 M2-3：Fluence

- 选择 surface crossing、volume fluence 或 track-length 语义。
- 优先评估 Geant4 primitive scorer，避免重复实现无契约统计器。
- 定义方向、面积/体积归一化、重复 crossing 和权重。

### 7.5 M2-4：biasing 物理验证

- 为 analog/biased 建立同一几何、源、物理列表和固定种子场景。
- 比较期望值、方差、收敛和性能，不以 operator 挂接作为物理正确证据。
- 记录可接受误差、样本量和统计方法。

### 7.6 M2-5：参考场景和基准库

- 为 hits、Edep、LET、Dose、Fluence 和 biasing 建立最小参考场景。
- 保存输入、软件版本、随机策略、参考输出和容差。
- 将快速回归与长时间物理 benchmark 分开。

M2 完成门槛：每个开放 scorer 都有物理定义、单位、输出 schema、ST/MT 行为和参考结果；未达到门槛的开关继续 fail-fast。

## 13. 原子提交策略

每个提交只完成一个可命名工作包，并满足：

- 提交前记录 HEAD、`git status --short`、staged 文件和保护 blob。
- 混合文件使用 `git add -p` 或等价精确 patch；禁止 `git add -A`。
- 测试产物、缓存、用户文件和交接快照不进入功能提交。
- 代码、测试、必要文档在同一原子提交中闭环。
- 未经用户授权不得提交或推送。
- 提交后再次验证提交内容、工作区剩余改动和 `.gitignore` index blob。

当前推荐提交序列：

1. B2B2 已提交 `018345c fix(geometry): report source-aware config warnings`。
2. GUI 演示改动提交，主题/i18n/布局/预览可在复审后决定一个提交或少量独立提交。
3. `feat(gui): close generated and external run inputs`，仅包含 M0-3C0A。
4. 后续每个 C0B、C4、D、E、B3 工作包独立提交。

## 14. Agent 执行提示词规范

交给执行 Agent 的提示词必须包含以下内容：

1. 工作包名称和唯一目标。
2. 必须读取的 `AGENTS.md`、相关文档和代码事实来源。
3. 当前分支、HEAD、staged 保护项和禁止操作。
4. 允许修改的文件或模块，以及明确禁止触碰的混合改动。
5. 配置解析、校验、运行时、GUI、测试、文档六层要求。
6. 已知缺陷和不得采用的伪修复。
7. 必须运行的测试及环境缺失时的报告方式。
8. 原子提交边界；是否允许暂存、提交、推送必须单独说明。
9. 最终报告必须区分实现、验证、提交和未验证部分。

```text

目标：
- <唯一、可验证的目标>

禁止范围：
```
