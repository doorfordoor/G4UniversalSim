# 环境辅助安装

安装入口可为 Windows/Linux 的运行环境和开发环境形成安装方案，并在用户确认后校验、暂存和发布文件。安装包的应用版本、Geant4 版本和实际能力分别显示；不是看到某个版本号就拥有该版本的全部可选功能。

## 四种事实分别判断

| 事实 | 判断依据 | 不能据此推断 |
| --- | --- | --- |
| 文件已安装 | 执行收据记录实际校验、解包和发布；警告另行保留 | 后端和必需数据已经可用 |
| 环境就绪 | I1 重新检查实际后端、能力和必需数据 | 配置已初始化或事件已运行 |
| 模拟完成 | K1 核验本次进程、摘要和逐轮计划/完成事件等证据 | 物理结果已验证 |
| 物理验证 | 指定参考、判据、输入和适用范围的独立对照 | 任意场景均正确 |

安装和选择环境均不会启动模拟。文件发布后仍须检测、显式选择环境，再按通常流程校验和运行项目。

## 选择运行环境或开发环境

**运行环境（runtime）**用于运行程序，包含相应后端、桌面程序及交付清单声明的依赖；完整交付来源还须包含匹配的 Geant4 数据。用户运行这类包不要求先安装 CMake 或 C++ 编译器。包内 Python 辅助程序用于交付工具及科学数据处理，本轮已实际验证 ROOT 读写；它不承诺替代任意第三方 Python 开发环境。

**开发环境（SDK）**用于编译 Geant4 consumer 或交付包中的应用源码。SDK 文件已安装与编译成功是两件事：编译还需用户已有且可用的 CMake、C++ 编译器、适当的生成器及系统依赖。程序记录实际工具路径、解析后的可执行文件和散列，再执行配置、编译、链接与运行探测；不会自动安装 Visual Studio、编译器或修改现有系统环境。大规模源码编译另有时间、内存和磁盘成本，不能把安装计划中的文件暂存空间当作整个编译过程的资源上限。

当前已有实际验证的交付流程为 Windows/Linux x86_64。清单格式能表达其他架构，不表示已有该架构产物或验收。11.2 不因已有版本矩阵而自动纳入本轮交付。

## 从界面安装

1. 打开主界面的“环境”，进入“环境发现与诊断”，选择“安装运行环境…”。已有后端路径会作为检测候选；没有指定路径时，发现过程读取环境变量和 PATH 中的候选。
2. 选择运行环境或开发环境。版本列表中的“发布包版本”是应用交付版本，方案另列声明的 Geant4 版本及 SDK 工具需求。
3. 加载发布方提供的安装清单，选择安装所在目录，并填写一个**新文件夹名**。已有环境不覆盖，安装前缀不得指向未知占用目录或链接。
4. 先“检查安装方案”，查看目标、来源、大小、许可、空间需求和拒绝原因。此步骤不联网、不下载、不写安装目录，也不启动后端。来源可信后，再执行“安装此方案”；联网下载还须显式允许。
5. 文件发布后，环境列表重新检测新安装；若已有检测正在进行，会在该轮结束后再检测。原有候选保留，项目环境不自动切换。用户选中条目后使用“使用所选环境”。

程序尝试读取交付目录内的 `install/catalog.json`。开发源码中的示例清单不提供正式发布版本。没有随包或发布方清单、清单为空或没有匹配平台/用途时，界面没有可安装条目，需用户提供真实清单。项目当前没有可据此承诺自动发现所有版本的公共 catalog 服务，也不会补造公共下载地址。离线交付应连同其相邻产物整体搬移；相对来源以清单当前位置为锚点校验，不能依赖构建机的绝对路径。

清单须给出确切产物、大小、SHA-256、许可与解包目标。SHA-256证明字节符合清单，不能代替对发布来源的判断。联网来源为清单中明确列出的受校验 HTTPS 产物；安装器不根据版本名自行拼接未经核实的下载地址。平台不符、版本不兼容、路径越界、链接和未知目录占用等会拒绝执行。

## Geant4 版本、数据与 GDML

应用发布包版本与 Geant4 版本是独立信息。正式组装要求 runtime、SDK 和数据的 Geant4 身份兼容，不能把同为应用1.0.0的11.3运行包与11.4 SDK混装。数据组件必须真实取得并通过清单校验；构建机上存在数据目录不能代替干净机器上的交付。

能力由实际后端报告。当前所用官方 Windows Geant4 11.4.3 SDK **未启用 GDML**；安装成功也不会将该能力变为可用。对应实际测试检查导入/导出的明确拒绝、未发生事件输出且未覆盖输入。11.3或其他平台的GDML成功不能据此给11.4此构建标为支持。

独立 Xerces 字节捕获组件的检查与后端 GDML 能力分别计证。显式选择同源检查 helper，可以验证文件/依赖的实际字节捕获、失败收尾等组件契约；它既不启用官方11.4后端的GDML，也不证明完整GDML几何或物理行为已经验证。

## 取消、恢复、核验与卸载

安装中可请求取消，取消在服务检查点生效。关闭正在安装的窗口也先请求取消并等待收尾，不表示所有文件操作立即终止。执行收据记录实际到达的阶段及是否留下可恢复的事务。

重新打开安装窗口，选择原父目录和文件夹名并检查方案。合法的中断事务可提供“继续上次安装”及清理临时文件的操作。恢复须与原计划、前缀及事务身份相符；缺少可核验计划的旧事务只能清理。清理须明确确认，只处理该事务拥有的临时文件，不删除已安装文件或其他环境。多进程使用同一前缀时由系统级排他锁保护。

发布后清理失败会保留“文件已安装但有警告”，不反写为未安装。安装报告包含计划及真实执行收据，保存到新文件，不静默覆盖旧证据。GUI中的事务清理不是卸载。

命令行另提供安装核验和独立卸载。卸载按受管收据检查文件身份，并处理其拥有的安装内容；它不是任意目录清理器，也不代表GUI已经提供一键卸载入口。已改动或不属于本次安装的文件不得被当作可任意删除的内容。安装事务失败恢复与卸载恢复各保留实际收据。

## 命令行

从源码环境执行 `python packaging/install_plan.py --help` 查看当前参数。入口包括：

- `plan`：离线形成计划；提供清单、profile、平台/架构、发布包版本、安装前缀及允许根目录。
- `execute`：执行已保存计划；联网需 `--allow-download`，继续事务用 `--resume`。
- `inspect`：只读取已保存的可核验事务计划，不自动继续或清理。
- `verify` / `uninstall`：按受管安装身份核验或独立卸载。
- `recover`：清理事务或恢复未完成卸载；只处理相应事务拥有的范围。
- `probe-sdk`：显式指定新构建目录和 CMake，可选 compiler/generator；`--kind consumer`检查Geant4 consumer，`--kind application`编译交付的应用源码。

使用全局 `--output` 时，参数放在子命令前，例如 `python packaging/install_plan.py --output 新报告.json plan ...`；目标必须是新文件。SDK探测的成功只指收据记载的配置、编译、链接及执行范围，不等同于模拟完成或物理验证。

## 验证依据与边界

本轮实际覆盖计划正反例、路径/链接拒绝、校验下载、跨进程锁、取消与新进程恢复、受控安装/核验/独立卸载；Windows/Linux的runtime与完整SDK流程、SDK consumer和应用源码编译均有实际收据。完整包另验证Geant4数据、ROOT辅助读写及带3D的冻结桌面启动和正常退出；不能用无3D降级包代替带3D桌面验收。

全新CI宿主的完整安装与卸载由 `.github/workflows/full-installation.yml` 执行；桌面冻结/ROOT交付由 `.github/workflows/desktop-package.yml` 单独验证。它们与本机受控前缀、清理PATH的检查分别保留身份，不互相冒充。失败的历史构建、缺工具、依赖缺失和门禁拒绝报告不追改为成功。每次引用结果应关联实际提交、平台、源码/产物散列及对应收据。

本页说明产品行为和验收边界。项目级阶段状态、最终提交映射和证据入口以 STATUS、ROADMAP 与该轮最终归档为准；安装收据不替代I1环境事实、K1本次运行事实，也不恢复旧项目的验证资格。
