# 受控运行会话协议（g4usim-session-v1）

本文描述后端 `--session-server` 模式下 stdin/stdout 上的 JSON 行协议，以及
`--session-record-dir` 中的逐轮记录。它是 F2“受控多轮运行会话”的第一版实现
契约，协议名固定为 `g4usim-session-v1`。GUI 面板已按 §7 接入本协议（作者交付，
待独立复验）；外部驱动目前只有测试脚本。本文件只描述后端实际实现，不把“已注册
能力”当作已验收的 GUI 功能。

## 1. 启动方式

```
G4UniversalSim.exe --config <main.ini> --session-server \
    --output <输出目录> --session-record-dir <绝对记录目录>
```

- `--session-server` 不能与 `--ui`、`--macro`、`--dry-run` 组合。
- 必须显式给出 `--config` 与 `--session-record-dir`。
- `--session-record-dir` 必须是绝对路径，且不能位于 `--output` 之下；违规在
  Geant4 初始化前失败（`G4UniversalSim fatal error: ...`，非零退出）。
- 一次进程只服务一个会话；会话结束后进程收尾并写 `run_summary.txt`。
- 现有批次、`--ui --ui-session csh` 与 dry-run 行为不变；`--ui` 下的原生
  （非 csh）UI 仍被拒绝。

能力自描述见 `--capabilities` 的 `session` 段：协议名、launch/record 参数、
handshake 要求、取消能力等级、可编辑源字段、JSON 解析器版本与许可证哈希。

## 2. 传输与帧格式

每行一个 JSON 对象（UTF-8，`\n` 分隔）。帧大小上限 65536 字节；超限视为
协议错误并结束会话。客户端先发 `hello`，之后才允许请求：

```json
{"kind": "hello", "protocol": "g4usim-session-v1", "client": {"name": "..."}}
```

服务端应答 `welcome`，其中含 `session_id`、`protocol`、`backend`
（`source_fingerprint` / `build_git_commit` / `compiler_id`）、`limits`
（`max_frame_bytes`、`max_events_per_run`）以及初始 `state`。

请求帧：

```json
{"kind": "request", "seq": 1, "id": "000000000001",
 "request_id": "000000000002", "op": "get_state",
 "params": {}, "state_revision": 0}
```

- `seq` 从 1 起严格递增 1；重复 `seq` 在幂等窗口内返回缓存响应（`duplicate=true`），
  否则以 `out_of_order` 结束会话。
- `id` 与 `request_id` 是 1–64 位十六进制字符串；`id` 标识帧，`request_id` 标识
  幂等请求。
- 变更类请求（除 `get_state` 外全部）必须带与当前状态一致的 `state_revision`，
  否则 `stale_revision`；`set_source` 这类纯拒绝可以继续会话。
- JSON 顶层必须是对象；重复键、非有限数字、嵌套过深、非法 UTF-8 转义与非对象
  根均以协议错误结束会话，不会带异常终止进程。
- 响应帧带 `kind=response`、`seq`、`id`、`request_id`、`op`、`status`
  （`accepted`/`applied`/`ok`/`rejected`）、`state_revision`、`duplicate`。

## 3. 操作与语义

| op | 状态要求 | 成功响应 | 主要拒绝 |
| --- | --- | --- | --- |
| `get_state` | 任意 | 当前草稿与内核状态 | — |
| `initialize` | 未初始化 | `/run/initialize` 已执行（`applied`） | `already_initialized` |
| `set_source` | 空闲、单源、可编辑 | 请求/解析结果分开报告 | `busy`、`stale_revision`、`source_unavailable`、`invalid_value`、`unknown_field` |
| `run` | 空闲且已初始化 | `accepted`，随后 `run_started`/`run_finished` | `busy`、`kernel_not_initialized`、`invalid_params` |
| `cancel` | 仅运行中 | `accepted`（`soft_abort_at_event_boundary`） | `not_running`、`unknown_run`、`stale_revision`、`invalid_request` |
| `ping` | 仅运行中（读取线程） | `ok` + 当前阶段 | — |
| `shutdown` | 空闲 | `accepted` + `closing` | `busy` |

- `set_source` 只允许 `particle`、`energy`、`position`、`direction`、
  `plane_beam` 五个字段；多命名源（`[source.<name>]`）、相空间源、高级 GPS 源与
  离子源不能经会话编辑，需改主 INI 后新进程启动。
- `set_source` 的响应同时给出 `requested`、`resolved`、`application_status`
  （`configured`）、`evidence_level`（`unknown`）与 `kernel_evidence`
  （`not_observed`）：这只表示 SourceManager 接受了设置，不表示 Geant4 内核已
  消费。内核消费证据只能来自逐轮 `run_finished` 的 receipts/artifacts，以及需要
  另行解释的物理输出；不得用 `event_edep` 的数值代替源能量消费证据。
- `run` 的 `params.events` 必须为 `1..100000000` 的整数；同一 `request_id` 重复
  发送返回缓存响应且不会重复运行。
- 运行中的 `ping`/`cancel` 由读取线程快速应答，但它们与主请求路径共用同一套
  身份规则：`cancel` 必须携带与当前状态一致的整数 `state_revision`，目标类型
  （`run_request_id` 字符串 / `run_id` 整数）与目标值也必须匹配；缺失、类型错误
  或过期 revision 都被拒绝，且不修改取消标志，合法 run 继续运行。被拒绝的请求
  与主路径一样消费其 `seq`。
- `request_id` 的幂等指纹覆盖 `op` 与 `params`（不含 `seq`/`id`）：同一
  `request_id` 携带不同 `op` 或不同参数时返回 `idempotency_conflict`，不会被当作
  重复请求复用缓存。
- `cancel` 在读取线程中登记原子取消意图并立即应答；各 worker 在自身线程的
  `RunManager` 完成本事件记账后调用 `G4RunManager::AbortRun(true)` 软中止
  （`src/Actions/EventAction.cc:60`，不是由主线程直接中止）。被取消的轮次仍生成
  运行收据，状态为 `cancelled`，`completed_events` 小于 `planned_events`。取消
  能力仍标为实验性：已验证 Windows 双 worker 的真实取消与“取消后下一轮不受影响”，
  跨平台与更复杂的物理列表尚未验证。
- `ping` 只在运行中由读取线程应答；空闲时按普通请求处理。
- `shutdown` 空闲时接受并发送 `closing` 事件（`reason=shutdown_requested`），进程
  以 0 退出；stdin EOF 在空闲时同样以 0 退出，但只在记录文件中写入
  `direction=meta`、`event=eof_close` 的收尾条目，不发送 `closing` 帧。

## 4. 运行事件与收据

`run_started`：`run_request_id`、`run_id`、`planned_events`、
`cancel_requested`、`state_revision`。

`run_finished`：`run_id`、`planned_events`、`completed_events`/
`aborted_events`、`status`（`completed`/`cancelled`/`aborted`/`failed`）、
`cancel_requested`、`artifacts`、`receipt`、`receipt_path`、
`receipt_integrity`。该帧保持在 64 KiB 以内：当 artifacts 与收据过大时，帧改为
携带 `artifacts_truncated=true`、`artifact_count` 与 `receipt_ref`
（`path`/`schema`/`sha256`/`size_bytes`），由已关闭的收据文件承载完整列表；
不会用无归属的 `frame_too_large` 替换终态，也不会在缺少终态时假装成功。

`--session-record-dir` 是**记录根**，由服务端创建；每次会话在其中使用唯一的
`session-<session_id>` 子目录，因此同一记录根上的后续会话不会截断或覆盖历史
文件。`get_state` 的 `record_root` 是记录根，`session_root` 是本会话子目录。
每轮收据写入该子目录的 `run-<4位 runID>.json`，schema 为
`g4usim_session_run_receipt_v1`，包含计划/完成/中止事件数、状态、取消标记、
运行期源快照（`source`）与 artifacts 列表。记录目录还包含 `session.jsonl`：
逐帧 c2s/s2c 文本、会话级 meta（`eof_close`/`session_end`）。收据只能证明会话
层完成情况与文件写出；它不替代物理基准。

## 5. 输出与记录边界

- 会话输出仍写 `--output` 目录，沿用既有 CSV/ROOT 契约、线程后缀与 run_summary。
- 记录根不属于输出目录（按规范化绝对路径与平台大小写规则判断，相对路径按进程
  工作目录解析）；收据与 `session.jsonl` 是会话层审计材料。记录写入、关闭与失败
  锁存由同一互斥量串行化；关闭失败会使进程以非零退出，不会只报告成功。
- stdout 上除 JSON 帧外可能混有 Geant4 启动日志与物理列表信息；客户端必须按
  “可解析为 JSON 对象且含 `kind` 字段”识别帧，不能假定 stdout 全部是 JSON。
- 会话错误分两级：请求级拒绝（响应 `status=rejected`，会话可继续）与协议级错误
  （`kind=error`，非零退出）。源命令的古老致命路径（csh 下 `G4Exception` 终止）
  不受本协议影响，见第 6 节。

## 6. 与既有入口的关系

- csh / batch / GUI 的失败传播保持不变：本协议新增入口，不改变旧路径。
- 原生 `/gps/*` 命令仍可直接使用，但它们会绕过会话的草稿与证据链；csh 实验已
  证明原生 GPS 与 SourceManager 缓存可能不一致，因此首版白名单不含原生 GPS。
- 会话的源编辑只覆盖单源简单源；几何、物理、计分、输出目录、线程数与 seed 仍
  需新进程（配置层）设置。

## 7. GUI 会话面板

Run Console 顶部新增“连续运行会话”区。它与普通单次运行不同：一次启动保留同一个
后端进程，面板通过上面的 JSON-lines 协议完成多轮 A/B/A，而不是每轮新开进程。

- **入口**：Run Console 的 Session 区 Start 按钮；至少要求 generated 输入模式且
  当前无普通运行、扫描或配置 Agent 占用进程。会话生成包沿用既有
  `create_run_package`，然后以 `--session-server --config ... --output ...
  --session-record-dir ...` 启动；记录根由 GUI 放在输出目录之外。
- **四区**：当前会话与本轮、下一轮参数、轮次记录、操作反馈。顶部状态 chip 区分
  Starting / Initializing / Ready / Running / Closing / Closed / Failed。
- **可编辑字段**：只有后端 `CanAcceptSessionEdit` 允许的单源普通字段（particle、
  energy、position、direction）与事件数；几何、材料、物理、线程、输出根显示
  “需新建会话”，不会被当作热修改发送。外部宏与高级源保持普通运行入口。
- **状态与回执**：草稿、待确认、已接受、被拒绝、需重启由实际回执驱动；配置被接受
  不等于内核已采用。`run_finished` 后 GUI 读取 inline receipt，或按
  `receipt_ref` 的路径、大小、SHA-256 校验后读取完整收据；`receipt_integrity=
  unavailable`、未知值、缺失或校验失败时该轮只显示“运行完成但记录不可用”，不
  显示完整成功。会话进程的退出码不会被当成模拟成功。
- **轮次记录**：每轮保存 run/request 身份、参数、事件数、状态、收据校验结果；历史
  页只刷新只读信息，不复用旧轮次给当前配置重新授予成功资格。
- **取消与关闭**：运行中可用 Cancel；关闭窗口、shutdown、进程崩溃与 EOF 都有有界
  清理，只结束本会话自己的进程，不按进程名杀其它任务。取消后下一轮仍可运行。
- **重放入口**：会话正常关闭且至少完成一轮后，面板的“重放已完成会话”按钮可用；
  点击后在新后端进程中从已捕获的随机初态重放记录的轮次，写入新的输出与记录目录。
  不可重放时会话面板显示原因（见第 8 节）。
- **未覆盖**：本面板不实现断线重连、热改几何/物理；重放只覆盖由本协议产生的会话
  快照。

## 8. 完整随机初态重放

普通 `--session-server` 会话在会话目录额外保存两份重放身份，供另一个进程在新输出
目录恢复同一随机初态：

- `replay-snapshot.json`（schema `g4usim_session_replay_v1`）：会话开始时（首个
  run 之前）的 CLHEP 随机引擎状态（`HepRandom::saveEngineStatus` 原文与 sha256）、
  后端身份（`source_fingerprint`、构建提交、编译器、Geant4 版本）、线程数与 seed
  元数据、顶层输入文件哈希、输出根，以及配置阶段实际观测到的输入身份
  （`provenance`，来自 input provenance 的已消费记录）。Geant4 数据目录的内容身份
  在首轮运行前捕获，写入 `replay-data-identity.json`：每个数据集的文件数、内容
  SHA-256 清单摘要；读取失败或权限不足必须显式报错，不能静默跳过或只散列部分文件。
- `replay-manifest.json`（schema `g4usim_session_replay_manifest_v1`）：按顺序记录
  已接受的 `set_source` 与 `run` 计划（含 run_request_id/run_id/终态/完成事件数）、
  快照字节 sha256、数据身份摘要、线程与输出根。只有会话正常关闭（退出码 0）、所有
  轮次 completed、未取消且记录写入成功时 `replayable=true`；取消、失败、未完成会话
  写 `replayable=false` 与原因，仍需保留原失败记录。

重放入口（在另一个进程中执行）：

```text
G4UniversalSim --session-server --config <同一主配置> --output <新输出目录> \
  --session-record-dir <新记录目录> --session-replay <原会话目录>
```

- `--session-replay` 只能与 `--session-server` 同用，仍需 `--config`、`--output`、
  `--session-record-dir`；必须使用新的输出目录（与快照记录的输出根不同）。
- 启动校验分两段：**在回复握手或初始化之前**先做静态结构校验（会话目录可读；
  快照/清单严格 JSON；schema 版本；`replayable`；快照字节 sha256；后端
  `source_fingerprint`；Geant4 版本；线程数；输入文件哈希；数据内容摘要；输出根不同；
  整份步骤清单的结构与数值域：只允许 `set_source`/`run`；`set_source` 的字段与值长度
  必须合法，能量/半径必须有限且大于零；每个 `run` 必须带合法事件数、
  `status="completed"`、`completed_events == events`、合法 run_id 与请求 id；清单
  至少保留一个完成 run）。完成内核初始化后、**任何 BeamOn 之前**再做依赖内核的语义
  校验（粒子名必须存在于 `G4ParticleTable`，源编辑必须可解析），该预检是只读的：
  它使用 `ApplySourceEdit(apply=false)`，只做解析与 setter 同域校验，不修改
  SourceManager，避免后轮编辑泄漏到前轮。首个或后续任一步损坏都必须在任何物理运行前
  拒绝，不能先执行前面的轮次。CLHEP 引擎状态恢复后再保存一次，与快照逐字节比较；
  任一项失败都拒绝重放并非零退出，不运行任何物理。
- 实际终态核对：每个重放 run 的 `run_finished` 终态必须是 completed，完成事件数必须
  等于清单记录的 `completed_events`；结束时 `steps_executed` 必须等于清单中的 run
  步数，否则以 `replay_failed` 和非零退出结束。
- 校验通过后：先初始化内核，再比较当前实际消费的输入身份与快照 `provenance` 摘要、
  当前数据内容摘要与 `replay-data-identity.json`；然后按清单顺序重放
  `set_source`/`run`，每个 run 使用清单中记录的 run_request_id/run_id 身份，输出写入
  新目录。任一步失败发送 `closing{reason:"replay_failed"}` 并非零退出，不继续后续
  物理。
- 对照口径：逐事件/逐径迹按 `runID,eventID`（event_edep）与
  `runID,eventID,trackID`（hits）多重集逐字符串比较，保留重复行；仅排除墙钟/路径/
  性能元数据列（如 `run_wall_time_s`、`fom_per_s`），粒子物理 `time_ns`、路径长度、
  能量、权重与统计误差仍参与比较。线程分片文件是否逐位一致单独报告，不作为跨平台
  或跨线程逐位一致的承诺。
- 不重放：旧 csh/batch 会话（没有快照）、取消/失败/未完成会话、构建或数据身份不符
  的会话；不会用快照目录“偷偷”启动任何物理。
- GUI：会话面板的“重放已完成会话”按钮在会话正常关闭后启用，点击后在新后端进程与
  新输出目录完成重放，轮次表按实际 `run_finished` 与收据显示；不可重放时显示原因。

## 9. 明确未完成

- GUI 会话面板已接入本协议，但仅完成作者自测（Windows 离屏/实窗截图与真实后端
  三轮、取消、关窗）；Linux 实窗、125%/150% 缩放、真实收据不可用反例下的 GUI 路径
  尚未由独立复验覆盖。
- 取消在 Linux/MT 大物理列表下的有效性、取消期间输出文件完整性、断线重连尚未验收。
- 重放已在 Windows 本机以 1 worker 与 2 worker 实测逐事件一致；Linux 与跨平台、
  跨线程分片的逐位一致不在本实现承诺内。旧 csh/batch 入口没有快照，因此不可重放。
- 会话内不提供配置文件整体切换、重放历史 run、输出目录切换与随机种子修改。
- 本协议不改变 `G4UImanager::ApplyCommand` 的返回值语义，也不把所有 Geant4
  输出重定向为 JSON。
