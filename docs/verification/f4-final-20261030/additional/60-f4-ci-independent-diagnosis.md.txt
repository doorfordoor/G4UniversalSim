No C++ backtrace identifies a specific destructor. Glyph/legacy-output warnings are not a proven cause. Test 1 already closes/deletes/drains deferred deletes; simply adding this cleanup is not an adequate diagnosis.

## Conclusion and minimal proposal

**This is broader than missing-QVariant reads or a newly omitted QObject teardown.** Generic void-return methods themselves deplete None refs on this installed binding/runtime combination. The historical E6 guard reduced one hot path but cannot be assumed to fix all PySide6 6.12 / Python 3.11 calls. F4's new UI calls may push accumulated loss over the failure threshold; these experiments do not identify the exact failing call count in either original CI process.

1. Do **not** fix by `os._exit`, skipping tests, ignoring -6, adding artificial None references, or replacing only the highlighter getter and declaring success. Product field/navigation semantics need no change based on the current evidence.
2. First verify an isolated candidate PySide6/shiboken6 version, preferably existing Windows-tested **6.11.1** or another explicitly verified stable pair, under **Linux Python 3.11**. Do not change the running Windows matrix or global environment. Local Windows 3.11.9 currently reports PySide6 6.11.1, so its success does not cover the failing 6.12 environment.
3. If the previous stable pair has no None-refcount decay in the same absent/void/property controls and both original integration tests exit naturally 0, narrow `gui/requirements.txt` to that verified supported binding range/pair. Ensure workflows install through that single requirements source and record **Python/PySide6/shiboken6/Qt** versions in receipts. File list: `gui/requirements.txt`; a meaningful dependency regression smoke with ordinary void and absent-property reads (new or extend existing `smoke_qt_combo_data.py` after owner decision); runner registration only if new; affected docs/CHANGELOG. Add workflow inventory only if no existing receipt captures versions.
4. Acceptance: preserve all assertions/behavior in the two failing tests; natural process exits0 under Linux3.11; same minimal refcount controls do not decline after warmup; existing GUI static/integration matrix and real Linux dual-Geant4/M0OS receipts rerun on the actual new SHA/dependency environment; 13 native states remain required. A new library/version constraint is a compatibility fix and needs version evidence, not a speculative pin presented as proven.

No tracked code changed. New safety getter in product may be independently useful, but **alone is insufficient** given the void-method controls. Please relay this broader result to core agent to avoid spending the fix on only `diagnosticFocus`/i18n guards.
