# F1 GDML 异常与句柄关闭提案

2026-10-30，基线 HEAD `3d1faf1b256a945ac800c08bacf51db57f8ca416`。仅写 ignored `out/collab/f1-gdml-portability/`；受跟踪文件未改，主 exe 未重建，既有全量回归进程未操作。

## 已确认的问题

1. `tools/gdmlInputCaptureCheck.cc:82-95`：foreign、stdin、owner 三个故障测试只接受 `std::bad_alloc`。`D:/ProgramFiles/Geant4/include/xercesc/util/OutOfMemoryException.hpp:40` 显示 Xerces 的 OOM 继承 XMemory，不属于 std::exception 家族；main 的 std 捕获同样接不住。真实 Linux Geant4 11.4.3 / Xerces 3.3 日志 `out/verification/f1-ci-corrected/job-123960735990.log:1180` 为 `terminate called after throwing an instance of 'xercesc_3_3::OutOfMemoryException'`，有效证明异常族缺口。仅凭该日志不能精确断言抛出点在 foreign 线程或 owner 主线程；两处都存在未捕获出口。
2. `src/Geometry/GdmlInputCapture.cc:140`：FileBuffer 的 make_unique 在 try 外。原生句柄已取得，但该分配失败不能进入 :150 的关闭逻辑。新增确定性故障测试在 UTF 转换结束、释放 full path 后才武装下一分配，避免路径转换先消费故障；当前 Windows 实验在原 adapter 复现 `FAULT FileBuffer opens=4 closes=3 refused=1`，退出 1。
3. `tools/gdmlInputCaptureCheck.cc:78,97`：故障 adapter 的全局替换只在正常路径手动恢复。Check/异常退出会跳过 :97；capture 自身析构只恢复到该局部 fault adapter，而该对象即将销毁。提案使用局部 RAII 覆盖器，并增加正常与异常展开后的原 adapter 恢复检查。

## 两文件最小提案

`proposal.patch` 只涉及 `src/Geometry/GdmlInputCapture.cc` 和 `tools/gdmlInputCaptureCheck.cc`，`git apply --check` 已通过；未应用。

- 生产代码只将 FileBuffer 的 make_unique 移入既有 try，复用既有 source_.fileClose + rethrow。
- 两个 std::thread 均通过 std::exception_ptr 将异常转移至 join 后的调用线程；catch(...) 仅转送异常，不能成为期望失败判据。
- AllocationRefused 仅接受 `std::bad_alloc` 与 `xercesc::OutOfMemoryException`。顶层 catch(...) 明确报告非标准异常、返回 1，不计为成功。
- 保留全部原 Check 内容；增加 FileBuffer 精确故障、显式 Xerces OOM 读失败、非 allocation runtime_error 传播、正常与异常展开恢复 adapter 等检查。
- 原 foreign/stdin/owner 的 opens/closes 1/1、2/2、3/3 判定原样保留。新增 FileBuffer 4/4 与 Xerces 读失败 5/5；未知异常不能被 allocation helper 吞为期望 OOM。

## 当前实验和边界

独立 CMake 工程只链接当前 `D:/ProgramFiles/Geant4` 的 Xerces SDK（Windows Xerces 3.2 DLL），未链接/重建主模拟程序。`configure.log` 与 `build.log` 均成功，两个输出分别将加强后的同一 harness 链接原 adapter / 候选 adapter。

- `original-adapter.log`：正式 `scripts/test_effective_gdml.py` wrapper 退出 1；精确新故障点 `opens=4 closes=3`，其余此前原 Check 已通过。
- `fixed-adapter.log`：同一 wrapper 退出 0；`opens=4 closes=4`，最终 `opens=5 closes=5 adapter_restored=true`，`PASS native capture`。原始字节、写出、schema/entity、完整/部分网络、嵌套 scope 及替换后原字节 SHA 的原检查都保留。
- `probe.log`：由当前 `tools/test_assert_probe.py` 驱动正式 wrapper，最终状态另见该日志。
- `assertion-preservation.json`：机械核对原 Check 的文本标签全部存在，原 Python assert 未改；这是保留性检查，不是物理验收。

需下一冻结后在真实 Linux Geant4 11.3.2 / 11.4.3 矩阵重跑 integration effective_gdml 及正式证据门禁，不能把本机实验视作 Linux 验收或 F1 关闭。三种原故障触发所抛的具体异常族和故障消费位置依赖 SDK；新增 FileBuffer 故障点用明确释放边界去除该不确定性。

## 已审的无新增缺陷边界

`src/Geometry/GdmlInputCapture.cc:49,58-61,72,84-88,98` 的 non-owner、路径转换及 stdin 失败均在既有 catch 中关闭原生句柄；`Capture:150-154` 缓冲读取/ledger 异常也有关闭，map emplace 时原生句柄已关闭，unique_ptr 会释放缓冲。`Impl:231-239` 在所有可抛构造完成后才发布全局指针，析构恢复原 pointers；没有把该处误报成同一泄漏。close 本身抛出时是否仍实际关闭，属于底层 XMLFileMgr 的契约，当前实验未宣称覆盖真实系统资源耗尽/关闭失败。
