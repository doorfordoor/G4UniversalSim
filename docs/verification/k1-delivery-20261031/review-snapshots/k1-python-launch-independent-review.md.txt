## 剩余发现：[P2] 把选项值误识别为 --working-directory

位置：gui/g4usim_gui/core/backend_launch.py:98-110（尤其 :98、:100）。

helper 遍历全部 arguments 查找 flag/flag= 前缀，没有按后端 CLI 语法跳过 --run-name 等选项的值。runner.py:81-82、experiment_workflow.py:109-115 都原样发送用户 run_name，因此这是公开动作路径可到达的回归，短 cwd 同样受影响。

独立反例，实际使用 SHA af6c9ae0b257589f73316b81add1c58e394e37c5efc2e12b3e140605797d2c98 的开发后端，以现有短工作区为 cwd；仅做能力查询，不运行模拟：

## 其余限定入口检查

- helper 在宿主中只产生计划，未 os.chdir，未创建资源目录、8dot3/junction/盘符；UTF-16 计数保留尾分隔符/NUL，选择既存短祖先。绝对 program 在选择祖先前固定；项目 config/macro/output 参数不重写。逻辑 cwd 和 launch cwd 分开记录。
- environment_discovery._backend_command 仅接管后端 capabilities/data，原 _command 继续用于通用 SDK 工具；长路径能力声明严格要求 launch.working_directory is True。新 flag 被旧程序拒绝后归 unsupported_working_directory，不在祖先无 flag 重跑来伪造 ready。这个分支不授予缺失数据/实际模拟资格。
- workflow 的独立 inspect 和 run/init 内部 inspect 仍使用已有 _inspect QProcess，helper 只替换启动传输。inspect 完成后仍先核当前 snapshot/environment identity，随后才消费 plan；没有依据 launch cwd 重新规划/复制原始源文件。原始 external inspect 和隔离运行的区别保持。
- runner.start 默认与 custom command 都在 ensure_directory/open stdout/stderr 前验证 helper。拒绝时 last_result=failed、发 error、不打开日志；workflow._run_error 在非运行状态完成失败收尾。实际 QProcess Finished/FailedToStart 的原关闭路径仍在，unsupported 结果保持 failed，没有 summary 仍 incomplete。
- _run_finished 仍经 output_evidence、严格请求绑定及实际输入校验，transport 审计字段没有替换 UUID、actual_output_dir 或 F1 实际字节路径。raw draft/snapshot 捕获和资源 closure/export 判定未在本限定 diff 中改动；不会因为启动成功提高 unknown source-copy/外部 macro 的覆盖等级。
