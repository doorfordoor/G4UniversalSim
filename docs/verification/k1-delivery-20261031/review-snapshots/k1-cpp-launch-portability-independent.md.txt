## 审查范围与结论依据

审查 main.cc、CMakeLists.txt、include/Core/BackendCapabilities.hh 的当前 Git diff，以及新增 cmake/WindowsRuntime.cmake 和 scripts/test_backend_working_directory.py；沿调用链只读核对 Geant4DataLocator、environment_discovery 的 None overlay、backend_launch、测试登记、Linux workflow 和 F5 初始真实输入夹具。所审五文件首尾 SHA 一致，见末尾。

### Linux 两版本：相同测试成立，真实运行仍待矩阵

- 测试 line110–123 从实际环境报告提取每个 dataset 的 env/folder，未写死 11.3/11.4 的版本目录。先清 GEANT4_DATA_DIR 和全部已报告 G4…DATA，再在 bundle_root/relative-data 创建各目录；覆盖相对数据目录的 cwd 解析，不读取这些空目录的数据内容。
- 核对 Geant4 11.3.2 与 11.4.3 上游 G4FindDataDir.cc：两版均先检查单数据集环境变量，再按 GEANT4_DATA_DIR 查找已知数据集目录；该逻辑用 is_directory 判断，不要求目录内有 transport 数据。因此空目录用于此次 discovery 正例是有效夹具，不是 transport 的假数据。
- 错误 cwd 下，项目 ApplyGeant4DataFile 会报告相对目录不存在而不设置 GEANT4_DATA_DIR；内核仍可能从编译默认位置找齐真实数据。line127–129 只要求 geant4_data_dir 为 None、note 不同及错误根没有 relative-data，不要求 required_complete=false。这在 Linux conda 安装上尤其必要，属于正确负例语义，不是降门禁。当前 Windows 独立负例也实际观测 required_complete=true、geant4_data_dir=null。
- None overlay 在 environment_discovery.py:38–47 对 os.environ.copy() 执行 pop，而非写入字符串 None；不会污染主进程。后续服务 transport 仍使用原 executable 和未覆盖的真实环境（测试 line132–138），未把 copied discovery 进程或 data_env 传给 transport。
- Linux 的长路径构造每段长度远小于常规 NAME_MAX，累计约数百字节，未依赖 Windows 盘符、扩展路径前缀或 UTF16 文件系统实现；UTF16 计数只是为 Windows 反例设置下界。copy2 保留 POSIX 执行权限。CMake 仍用既有外部库链接路径；复制后的 Linux ELF 动态库可加载性须由对应 CI 运行证明，Windows 结果不能替代。

上游依据：[Geant4 11.3.2 G4FindDataDir.cc](https://raw.githubusercontent.com/Geant4/geant4/v11.3.2/source/global/management/src/G4FindDataDir.cc)、[Geant4 11.4.3 G4FindDataDir.cc](https://raw.githubusercontent.com/Geant4/geant4/v11.4.3/source/global/management/src/G4FindDataDir.cc)，重点 line72–111。此处只引用目录发现行为，不据此推断数据内容或物理正确性。

### early cwd / error / datafile

- main.cc:584–600 先做纯命令行解析，检查唯一、非空、绝对、存在目录，再用 error_code 的 current_path 切换。相对/不存在/文件/重复参数均在 SimulationManager 构造（line602）和 Geant4DataLocator（line608）之前返回非零；不会经过正常收尾去祖先目录写失败摘要。is_directory 成功但 chdir 因竞态/权限失败时，也走独立 Cannot apply 错误，未继续读取输入。
- 正常 cwd 后才解释 config/macro/output、读取 geant4-data.txt 的相对目录值。保留原 argv0 的绝对基础（line593）使 Linux 上以绝对或带目录的相对 executable 调用时，不因 chdir 把 sidecar 定位到目标输入目录。Windows locator 仍用 GetModuleFileNameW。
- 此项没有改变 sidecar 相对目录值的解释策略：文件在程序旁查找，文件内 relative-data 相对最终 cwd。测试正反对照实际检查后端报告的 dataset path，不止 Python 的 requested cwd 回显。
- capabilities.version 仍为 1，新增 launch.working_directory 为真正 JSON bool；它表示后端可执行该入口，不代表任意依赖或任意路径运行都成功。

### Windows runtime / 测试门禁

- WindowsRuntime.cmake 仅 WIN32 AND MSVC 时为该 target 生成、嵌入 longPathAware=true 与 activeCodePage=UTF-8；Linux 不生成 manifest，也不加 Windows 编译/链接参数。CMakeLists.txt:43–55 已把 *.cmake 纳入源码指纹与 configure 依赖，新增模块没有绕过构建身份。
- 不以注册 capability 代替实现：既有 r3 EXE 内 manifest XML 和 capability bool 已独立核对（下节）。现代 Windows/系统长路径策略前提保持，不能推断 MinGW 或第三方组件全面支持。
- 新测试保留真实 CLI inspect、真实 3/3 transport、初始化 no_run、后续服务真实 run、summary/output_failure 状态、effective snapshot/metadata 存在及临时发布清理、祖先同名错误输入 SHA 未变、逐条 F1 实际路径/归属/内容 SHA。错误目录六例仍非零、stdout 空且摘要集合不增加。不是靠减少断言或把 skip 变 pass 处理旧反例。
- runner 将此项登记为 integration 的 qt/exe 用例；现有 Linux workflow 用同一 built executable 跑 integration，并有 fail-on-skip 与报告证据门禁。新增测试并未替代原统计/物理测试，也没有修改其容差。
