## 实现边界

1. 参数入口：project/bundle 二选一；运行环境覆盖 executable/runs root；`--records` 对应服务 `records_root` 目录。inspect/validate(fields|initialization)/apply/generate/run/evaluate/export 全部路由到同一服务，不调用 shell、不直接启动后端、不复制业务校验或成功判定。
2. apply：只接受严格完整 `g4usim_edit_snapshot_v1`，无任意路径 setter；`snapshot_from_dict()` 重建后经 `workflow.apply(..., expected_revision=session.revision)`，核心接受后才 `save_project(project_for_snapshot(session.current()), --save-project)`。无直接编辑 session 的产品旁路。测试 double 内的 session.replace 仅模拟服务接受。
3. 事件循环：QCoreApplication + QEventLoop/QTimer，先订阅 completed 再派发；兼容同步 terminal 返回与 pending 后异步 completed。SIGINT/SIGTERM 标记由 Qt tick 消费；超时/取消调用核心 cancel，升级 force 并清理注入的 runner/inspect QProcess，有界等待。服务 cancel 抛错仍继续清理，不按进程名停止其他任务。迟到 passed 不能覆盖 timeout。
4. 输出：正常动作与错误为单行 `g4usim_experiment_cli_v1` JSON；依赖与动作打印移到 stderr。仅服务 passed + 所需保存成功可退出0；failed/stale/unobserved/取消/超时及缺终态非零。ValidationReport 走自身 to_dict，其余未知对象拒绝。--help 为标准帮助文本。
5. 历史：CLI 不读取历史来恢复信任；records_root 交核心。bundle.load_bundle 的历史保持 transient 中 stale 记录，不注入新的可信结果。
6. bundle：严格使用已核验 load_bundle 与其 replay_inputs；run/inspect/initialization 时把运行入口选为 external、当前包根作工作目录、选定新后端，使相对依赖不经旧 writer 再复制。此处仅选择已有受支持入口，不自行解析 macro/INI。generate/apply 仍针对完整编辑 snapshot，不将闭包重放伪称生成支持。
7. evaluate：JSON 比较数组及显式 run ID 原样交核心，未接收外来 pass。跨 CLI 进程的 run ID 恢复、持久记录与 fresh 身份检查需核心联调确认。

本次与前版 API 的差异已收敛：使用构造器 session/runner/inspect_process/records_root；不传前版构造 apply_snapshot，不用 history/recordChanged/stateChanged；apply_snapshot 可选投影回调由核心自身处理；多数动作不再传 expected_revision。
