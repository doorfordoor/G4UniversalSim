## 1. [P1] Apply 接受非法非 seed raw draft，随后可生成与显示草稿不同的配置

位置：`gui/g4usim_gui/core/experiment_workflow.py:115`（`_field_report`）、`:126`（仅 seed 专门检查）及 `:452`（apply）。

**实际复现**：复用既有 `test_f5_transactions_backend.initial_state()` 在临时目录创建完整合法 WorkspaceSnapshot，保持 `sourceEditor.energy = '1 MeV'`，只把 `state['drafts']['config.source_editor_energy']` 改为 `'invalid energy'`。调用真实 `_field_report()` 返回 `can_run=True, errors=[]`；进一步调用真实异步 `service.apply(candidate, expected_revision=0)`：

```text
apply=passed
revision=1
typed=1 MeV
raw=invalid energy
```

此前一轮同一分支还执行 `service.generate()`，结果 `passed`，生成 INI 仍含 `1 MeV`。这不是 Geant4 物理通过，而是确定的服务接受/生成边界绕过。

**原因与影响**：`_field_report` 验证类型化编辑模型，只额外处理 seed、detail 和 `.raw` spin 文本，没有完整处理普通 QLineEdit 草稿与类型化模型的冲突。F5 的设计恰好允许保存非法 raw draft；其存在不能表示该草稿已被接受。CLI 可提交严格 codec 合法但 raw/model 不一致的完整快照；桌面 adapter 又会通过 `apply_workspace()` 恢复原始文本。结果是界面/恢复内容显示非法输入，服务却用旧模型给出 fields/apply/generate 通过。

**修复判据**：对受支持的完整草稿映射执行与 GUI 一致的接受/校验规则，不静默丢弃非法原文，也不能仅因为类型化模型仍合法就通过。至少以非 seed 源能量、物理 cut、几何表格原文等代表边界验证；合法格式差异不要一概按字符串不相等拒绝。apply 拒绝须保持 session revision/undo/redo/原快照，不能先投影后再补校验。GUI 与 CLI 应共用这一闭合规则。

## 2. [P2] Candidate 的同步克隆失败发生在 _begin 之后，服务永久 busy

位置：`gui/g4usim_gui/core/experiment_workflow.py:452-454`。

**实际复现**：在完成前一个异步动作、服务 idle 的条件下取得合法 `session.current()`，再设置 `candidate.state['version'] = 999`，调用真实 `service.apply(candidate)`：

```text
exception=Unsupported editing state version at project.editingState.version
busy=true
active.phase=preparing
```

`apply(None)` 也复现相同生命周期问题，但以上主反例使用的是被调用方公开接收的 WorkspaceSnapshot，而非只靠错误参数类型。

**原因与影响**：`_begin()` 已插入 pending 记录并占用 `_active`，紧接着 `clone_snapshot()` 同步抛错，尚未进入 `_work` 的失败最终化。后续所有动作被 busy 拒绝；cancel 只标 cancelled，没有在途 worker/process 能送回完成信号，因此也不能自然清除。

**修复判据**：在发布动作之前完成可同步拒绝的候选接纳，或保证任何 begin 后的同步异常走且仅走一次受控终态清理。拒绝后服务可继续下一合法动作、原 session 不变、无永久 pending/busy。对不支持 state 版本、来源文本不一致和错误 candidate 类型分别验证。

## 3. [P2] 事件样本以文本去重，数值相同的事件号可替代缺失事件并通过比较

位置：`gui/g4usim_gui/core/experiment_workflow.py:706`（`_compare_csv`），`:770-775`（标识文本 tuple 去重与之后的 int 范围检查）。

**实际复现**：使用真实当前 `_compare_csv()`、真实临时 CSV/严格参考 JSON，evidence 仅用内存对象提供已选 run N=2 和文件入口：

```csv
runID,eventID,raw_edep_MeV,weighted_edep_MeV
0,0,1,100
0,00,1,100
```

规格为合法的 energy_deposition / sensitive_total / raw / MeV / per_event / run=0 / mean_standard_error，参考值 1、零容差。结果：

```text
passed=true
sample_count=2
```

这里只有数值 event 0，缺少 event 1。字符串 `'0'` 与 `'00'` 被看成两个标识；之后又都能通过 `int(eventID)` 的 `[0,N)` 范围检查，于是 count==N 不能证明完整 N 个不同事件。

**修复判据**：在去重前统一严格解析 `(runID,eventID)` 的整数身份，或拒绝非规范十进制编码；最终验证恰为所选 run 的完整不同事件集合，重复/缺失均拒绝。保留多 worker 合并与逐 run metadata N，不能改成每 worker 都有 master N。反例属于比较消费者完整性验证，不宣称正常后端会输出带前导零的 eventID，也不把 F1 SHA 当来源签名。
