## 1. [P2] 指数溢出的 JSON 被接受为 ready，破坏严格事实协议

位置：`gui/g4usim_gui/core/environment_discovery.py:97-107`、`:110-131`；传播位置 `:269-284`，GUI `gui/g4usim_gui/widgets/environment_dialog.py:188-195`。

`_json()` 只用 `parse_constant` 拒绝 NaN/Infinity 字面量，未拒绝 JSON 数字 `1e999` 经 Python 转成 `float('inf')`。数据报告的未验证字段可携带这种值，`_data_report()` 原样返回。能力路径后续有 `json.dumps(..., allow_nan=False)`，数据路径没有相同检查，因而状态被发布为 available/ready。对话框默认 JSON 编码又将它显示成 Infinity，且允许选择。

**具体输入**：

```json
{"schema":"g4usim_geant4_data_v1","required_complete":true,"datasets":[{"env":"G4XDATA","folder":"X1","required":true,"found":true,"path":"/fixture"}],"geant4_version":1e999}
```

独立运行结果：

```text
parser_accepted=true
version_repr=inf
json.dumps(facts, allow_nan=False): Out of range float values are not JSON compliant
probe status=ready, identity.stable=true
Use selected environment enabled=true
details contains Infinity=true
```

直接 parser 调用是真实执行；probe 的 `_command` 使用内存合成能力/数据响应，二进制 hash 使用实际 Python 可执行文件；Qt 为 PySide6 6.11.1/offscreen，执行真实 `_completed()` 与控件状态查询。没有将 Python 可执行文件当作真实 Geant4 后端，也没有让合成 ready 冒充真实环境验收。

**影响**：违背文档“返回可由 `json.dumps(..., allow_nan=False)` 序列化”“非有限数值拒绝”的明确契约；后续 K1 canonical identity/记录持久化可在接受环境之后才失败，且已有“环境可选”状态无法代表严格协议已通过。

**修复判据**：在共同 JSON 边界拒绝任意层级的非有限数值，包含合法数字语法导致的指数溢出；数据路径必须保留 protocol_error，不能进入 ready。覆盖顶层附加字段、dataset 附加字段与嵌套对象，不只补查 geant4_version。拒绝后 GUI 不应因该次数据报告宣称数据已发现完整；是否仍允许仅选择能力可读的路径，应保持已有 partial 的明确语义。

## 2. [P2] 在裸名称按 PATH 解析前去重，会丢掉另一明确后端

位置：`gui/g4usim_gui/core/environment_discovery.py:323-332`；对比真实路径选择 `:242-245`。

去重 key 使用 `abspath(raw executable)`，但 probe 对裸名称另按子进程 PATH 执行 `shutil.which()`。两套规范化不一致：

```text
当前目录 W
PATH 中有 P/G4UniversalSim
输入候选 ["G4UniversalSim", "W/G4UniversalSim"]
```

若裸名称实际解析到 P（例如 W 中缺失该文件，或平台 PATH 选择 P），两个候选意图分别为 P 的真实后端与 W 的显式缺失路径。去重却先把两者都归成 `W/G4UniversalSim`，后一个完全不 probe，不保留其 not_found 诊断。在遵循 PATH 而不默认搜索 cwd 的平台上，W 也有文件时还可吞掉第二个真实后端。反向顺序则可能吞掉正常 PATH 候选。

独立内存反例：patch `probe_environment` 仅模拟上述裸名/显式路径的不同解析，patch host/sdk 为无操作，调用真实 `discover_environments()`：

```text
requested_candidates=2
different_intended_paths=true
observed_probe_count=1
explicit_candidate_probed=false
```

这个反例验证真实的去重分支，不宣称已在 Linux 启动两份后端。它不依赖执行任意未知程序，未产生测试文件。

**影响**：用户明确提供的候选及其错误诊断被静默丢弃，与“顺序保留、相同路径与相同环境覆盖去重”契约不符。不能从返回的一项结果推断另一候选也已探测。

**修复判据**：以与 probe 相同的子进程 env/PATH 规则解析候选，再按实际解析身份和环境覆盖去重；解析失败候选仍保留自己的失败事实。相同规范路径的别名可去重，实际不同路径绝不能被字符串预规范化吞掉。补两种顺序、PATH 裸名称与显式 cwd 路径、相同 exe 不同 env 的组合；保持子进程覆盖隔离。

## 已确认的边界与交接点

- 初始化与物理层：`probe_environment()` 仅执行能力与数据查询，ready 的文案只称协议可读/数据目录发现，不声称初始化、事件或物理通过。SDK 明确 `build_verified=False`，可选 Python 模块明确 `import_tested=False`。这些边界合理，不将未知 SDK 当作后端失败。
- 进程与线程：不经过 shell；直接子进程有各命令 timeout；缺库、加载器错误、超时、编码和协议问题分开。输出返回有长度限制，临时流文件的写入并不是全过程磁盘配额。文档也没有承诺终止全部后代进程，因此不把它误报为已违反的整进程树取消契约。
- GUI：后台 worker 经 QueuedConnection 发布；刷新清空旧候选、busy 拒绝重复刷新；关闭/代次失效丢弃旧回调；选择发副本；数据不完整允许选路径是明确设计，不能据此报告“假运行成功”。对话框控件逻辑 smoke 已独立执行，未作可见性/实窗签字。
- **环境覆盖交接仍需主代理裁决**：`discover_environments()` 支持同二进制不同 child env，且故意不回显环境变量值；`EnvironmentDialog.environment_selected` 只返回事实。当前 `window/experiment.py:134-144` 只把 facts.executable 写入项目，既不交接覆盖也不把所选事实交给运行服务。由此，某候选在覆盖 E 下探测成功，不意味着 runner 的继承环境 E0 可运行。此处作为已确认的接口限制，不归为 I1 自身新增确定缺陷：它声明只选择路径、不拥有运行。集成方应明确选择仅路径并在实际运行环境重新探测，或提供受控的激活上下文；不能静默把 E 的 ready 当作 E0 的证据，不能为此把完整 env/凭据写进配置包。
