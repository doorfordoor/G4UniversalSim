# 扩展组件、验证并继续开发独立工程

适用范围：AR5 当前源码布局与 K2 独立工程。以下命令供操作者在自己的新目录执行；已验示例不代表任意改动自动通过。CMake 内部静态库服务于同一工程的构建，不是稳定插件 ABI，也不是单独发布的 C++ SDK。安装 Runtime、源码导出、宿主 Geant4 SDK 和物理数据是不同的依赖与证据。

## 先确定改动由谁负责

| 组件 | 源归属与链接 | 优先验证 |
|---|---|---|
| 不依赖 Geant4 的共享逻辑（如 INI 读取、数值累计） | `g4usim_logic`：C++17、`include/`、`Threads::Threads`。例如 `IniReader.cc`、`HistoryStatistics.cc`。 | 直接测试原实现。如 `scoringNumericCheck` 仅链接此库；根项目的配置仍要找 Geant4，不表示此目标可独立配置整个仓库。 |
| 依赖 Geant4 的运行、计分、几何、输出与应用装配 | `g4usim_geant`：C++17，工程/生成头及 Geant4 头，链接 logic 与 Geant4；其私有定义包含真实构建配置。`G4UniversalSim` 只直接编译 `main.cc`，以 `native` 接后端。 | 用现有组件或真实接线的有限 probe；配置/初始化/事件/写摘要是不同层，不能靠其中一层代替其它。 |
| GDML 读写与输入捕获 | `GdmlIO.cc`、`GdmlInputCapture.cc` 是唯一有意允许的双编译。SDK 有 GDML 才有 `g4usim_gdml_native`（私有 `G4USIM_HAVE_GDML=1`）；SDK 无 GDML 或启用测试时建 stub。两者只向 logic/SDK 依赖，不反向依赖 common。 | 通过 `g4usim_link_backend(target profile)` 选一个：`native` 按 SDK 选 native/stub；`legacy` 保留旧无 GDML 的 parallel 组件；`none` 只连 common、适用不会引入 GDML 未决调用的 h2/random。不可同一进程链接两种 provider。 |
| 后处理与 repo-only probes | `mergeHistograms` 独立目标，不包含/链接 Geant4，有自身 `--source-fingerprint`；CMake 继续统一处理 Windows runtime。其他仓库专项 probe 放在相应 guard 内，不能擅自增加 standalone 组件标签集合。 | 现有专门 CLI、GUI 合并及 runner case；冻结 GUI 的 Python CSV 合并走应用 `scripts_dir()` 与 `script_python()`，不是这支直方图 exe。 |

新增 `src/**/*.cc` 要在 `cmake/BackendTargets.cmake` 三个成员表之一明确登记一次。CMake 比对生产文件枚举与声明所有权，会拒绝遗漏、多重归属；不要在每个 probe 再粘贴同一组 `SOURCES`。只有出现真实独立消费者才拆新目标。把 SDK 依赖、编译定义、include 与测试入口放在实际使用层；如果增加文件后缀或子目录，检查 CMake、Python 指纹、源码快照、模板各自的选择器，不要求四者收同一个集合。

**以 scorer 为例。** 先改真实后端，而后考虑配置/GUI：`ScorerDescription(id,type,enabled,settings)` 是值描述，`ScoringManager::RegisterScorerFactory(type,fn)` 接受无捕获函数指针，返回新的 `unique_ptr<ScorerBase>`。在配置阶段、Action 构造以前登记 factory，再 `RegisterScorer(description)`；登记实例 thread=-1，worker 重建传真实 thread id，不能把 master writer、累计器或可变资源藏在描述或全局。可共享的数据必须只读。旧 `RegisterScorer(unique_ptr)` 保留旧入口，不具备 Action 的重建描述，不可用作新可克隆 scorer。新 scorer 先做 Begin/End event/run、逐 run 清零、失败/首因和 MT/Sequential 的真实验证，再由配置读面明确支持键、单位、缺省和诊断；若未接 INI/macro/GUI，不对用户声称已有配置开关或动态插件。生产输出走现有登记/摘要，不直接写一份“看似成功”的替代收据。

**GUI 侧按现有接口接线。** 编辑写入沿 `EditSession` 与窗口投影，运行用 `ExperimentWorkflow` 对请求 revision 与输入做校验，再交 Runner/QProcess；`--capabilities` 是能力/构建身份，`--inspect-run` 是配置与 preflight，二者不是事件执行。CLI/菜单的独立工程导出复用 `core/export_project.py`，并受有限子集约束。新增 config/schema/GUI 入口时，把解析、拒绝、应用、writer、tests 和人类文档逐层对齐；不要把 GUI 字段、宏名或纯文本生成当运行支持。

## 源码改动如何进入新身份

1. 根 CMake 枚举 `src/**/*.cc`、`include/**/*.hh`、`cmake/**/*.cmake`，另加 `main.cc`、`CMakeLists.txt`、`include/Core/BuildInfo.hh.in`。新增/删除由 glob 的 `CONFIGURE_DEPENDS` 检查，**已知文件内容变化**由目录属性 `CMAKE_CONFIGURE_DEPENDS` 跟踪；再计算排序的 `相对路径:原字节SHA256\n`，对串接结果作 SHA-256。runner 的 `workspace_source_fingerprint()` 同算法。Git commit/source state 另记，比较编译输入 raw blob；无自有 Git 根的普通导出目录是 unknown，不能借上级仓库身份。
2. 重配后 `generated/BuildInfo.hh` 带新身份。main 通过 BackendCapabilities 包含它，还声明显式 `OBJECT_DEPENDS`；SessionServer 与 SimulationManager 直接包含它。头文件自身还会让真实 include 消费者重编。保新 build 命令、CMake cache、依赖图、对象编译/链接与 `--capabilities`/摘要；只看文件时间或最终 exe SHA 不足以证明依赖链。未链接受改对象的目标不强求二进制 SHA 变化；恢复原始字节会恢复 source fingerprint，但工具链输出未承诺逐字节可重现。
3. `tests_content_fingerprint` 与编译输入身份不同；它用 runner 规定的测试/fixture 等集合，并在计算时归一 CRLF。exe SHA、build source、probe/tool 源 SHA、SDK 身份、模板 digest、最终导出清单 digest 和运行 execution_id 各自登记，不互换。
4. `packaging/export_template.py` 调用实际 `collect_template_members()`：目前 cmake 仅顶层 `*.cmake`，tools 仅直接文件；include/src/schema/config/macros 递归，另含明确根文件/文档、许可证和 H2 真读的 `scenarios/semiconductor/niel/si_proton.csv`。新增 nested CMake 若被编译/包含，需要同步扩大模板与源码交付选择器并验证实际依赖，不能只因 workspace build 成功就发布。模板是实际复制的规范文本字节（CRLF、单独 CR → LF）；用户项目 raw/provenance 和发布后导出的严格校验不做这项归一。成员数动态：旧 309、AR5 r1 340 模板成员与其 S-A 349 个 export manifest 登记成员是不同历史集合，不是目标常量。

## 可操作路线：改组件 → 测试 → 导出 → 在独立副本继续

**A. 在隔离开发树完成组件改动。** 固定原提交、工作区脏变更归属、SDK 与基线报告。用新构建根；若做头/源增量证明，只在隔离树复用该树自己的 cache，并保变更前后编译日志/指纹。选择一个有真实消费者的改动，例如先以数值累计头 `include/Scoring/HistoryStatistics.hh` 或装配源 `src/Core/SimulationManager.cc` 的一行受控注释做“身份确实跟随”的工程正控。真正改科学算法时另需固定物理对照，不用注释结果给算法背书。

正式前先更新模板清单再执行任何读取模板的测试；否则旧模板拒绝是正确的（可作为负控）。下面两条只在该私有开发候选、完成成员变更评审后用，不能对原 export 调用：

```bash
python -B packaging/export_template.py --write
python -B packaging/export_template.py --check
```

下列 POSIX 例从仓库根运行；`$B`、`$SDK_CONFIG`、`$EXE`、`$MERGE`、`$REPORTS` 是操作者已确认的绝对路径。`$REPORT_JSON` 是本次 runner 输出的新 report.json，不指旧报告。SDK、编译器和 Geant4 数据须先按该安装自己的激活收据准备。Windows 采用下一步同形的 VS x64 或实际验证的 Ninja 配方，显式传对应配置 exe。

```bash
cmake -S . -B "$B" -G 'Unix Makefiles' -DCMAKE_BUILD_TYPE=Release \
  -DBUILD_TESTING=ON -DGeant4_DIR="$SDK_CONFIG"
cmake --build "$B" --config Release --parallel 4
"$EXE" --capabilities
python -B scripts/run_m0_tests.py --profile static --case build_identity --case k2_project_export \
  --executable "$EXE" --merge-executable "$MERGE" --report-root "$REPORTS" \
  --require-tracked-sources --fail-on-skip
python -B scripts/check_report_evidence.py --report "$REPORT_JSON" --require-candidate-identity
```

实际 scorer/运行改动按涉及面再选 `--profile backend --case scorer_factory`、`--case scoring_lifecycle` 或 `--case scoring_numeric`，同样明确路径与严格门；GUI 导出接线用 `--profile gui --case gui_export_project`，不替代冻结实窗。开发期追踪门只纳入归属已明确的新文件，不全仓暂存。

**B. 从改后候选产生全新独立工程。** 源码开发环境可将当前私有 checkout 的 `gui/` 放入本命令的模块查找路径，使用实际 GUI 依赖环境；从仓库根运行：

```bash
PYTHONPATH="$PWD/gui" python -B -m g4usim_gui.experiment_cli \
  --project examples/07_parallel_world_box export-project --destination "$E"
```

正式安装场景应从本候选真实安装 GUI 的 Project → Export Geant4 project… 分别导出固定 S-A（示例 07、external、seed 20261400、1 worker）与 S-B（默认单目标、generated、seed 12345、2 worker）。前述 CLI 是开发路径，不证明已安装的菜单/模板布局；复制运行包的 hits/event 合并是另一条链。E 必须新建，保 `export-manifest.json`、`export-template-manifest.json`、模板 origin、全部路径/长度/raw SHA 与输入读面；使用匹配候选 `verify_export(Path(E))` 严格核原 E。禁止为通过校验改写历史清单；export 内容、B 构建、O 输出分离。在相同 checkout 的 GUI 依赖环境中可实际调用（传入正确绝对路径）：

```bash
PYTHONPATH="$PWD/gui" python -B -c 'import json,sys; from pathlib import Path; from g4usim_gui.core.export_project import verify_export; print(json.dumps(verify_export(Path(sys.argv[1]))["identity"],sort_keys=True))' "$E"
```

**C. 从 E 本身独立配置、测试、运行。** 不是拿仓库或安装目录 exe 测 E。示例 SDK 配置目录是包含 `Geant4Config.cmake` 的实际目录。Linux 用同前 Unix Makefiles，源改为 E，并加 standalone；Windows 示例用仓库实际 preset 的生成器/配置，或复用 r1 实测 Ninja x64 已激活工具链。下例 `B`、`O` 均在 E 外且起初不存在。

```bash
cmake -S "$E" -B "$B" -G 'Unix Makefiles' -DCMAKE_BUILD_TYPE=Release \
  -DBUILD_TESTING=ON -DG4USIM_STANDALONE_EXPORT=ON -DGeant4_DIR="$SDK_CONFIG"
cmake --build "$B" --config Release --parallel 4
```

```powershell
# 对应 CMakePresets.json 的 VS 2026 x64；显式 -B 以保持原 E 闭包。
& $CMake -S $E -B $B -G 'Visual Studio 18 2026' -A x64 '-DCMAKE_CONFIGURATION_TYPES=Debug;Release' `
    '-DBUILD_TESTING=ON' '-DG4USIM_STANDALONE_EXPORT=ON' "-DGeant4_DIR=$SdkConfig"
& $CMake --build $B --config Release --parallel 4
# 已验 r1 的替代生成器：-G Ninja -DCMAKE_BUILD_TYPE=Release（x64 VS 开发环境）
```

核 Cache 的 source=E、build=B、standalone=ON、BUILD_TESTING=ON、实际 compiler/SDK。Ninja/Makefiles 的应用一般在 B 根，VS Release 在 `B/Release`，从实际目标确认。用此 exe 的 `--capabilities`、`--check-geant4-data` 绑定 BuildInfo、源和实际数据。每步保存真实 argv/cwd/PID/exit，stdout/stderr **分文件**，不得把 SDK 警告删除后解析拼接输出。以下以 POSIX 引用示例（Windows 用同一参数数组，保 `-C Release`）：

```bash
ctest --test-dir "$B" -C Release --show-only=json-v1
ctest --test-dir "$B" -C Release -L '^component$' --show-only=json-v1
ctest --test-dir "$B" -C Release -L '^component$' --output-on-failure \
  --no-tests=error --output-junit "$NEW_JUNIT"
cd "$E"
"$BUILT_EXE" --config project/main.ini --macro project/macros/run.mac --output "$O"
```

先严格解析清单 stdout：standalone 没有 `m0_*`，组件恰为 `h2_volume_scoring_check`、`parallel_scoring_component`。还须真执行两项、读新 JUnit 和完整 LastTest.log，确认未跳过/失败。组件测试不替代实际运行：每例独立 E/B/O，S-A 200/200、S-B 1000/1000，核单 run 与汇总、seed/worker、summary/metadata 的 build identity、实际输入角色和 output 闭包；S-A 多一个 parallel geometry，S-B 无。运行从 E 根，不在 E/project 下；`[parallel_world] geometry_config` 特例由后端相对主 INI 所在目录解析。运行后原 E `verify_export` 与逐字节清单不变。

**D. 独立继续改。** 另复制已验证 E 到新的 E-dev，复制后先验原清单一致。不要复制原 CMake cache/对象或在原 E 上改。若按旧 K2 §7.2 做可见的一行验证，仅在 E-dev 的 `SimulationManager::FinalizeRunSummary` 中、发布前的现有 `summary.Set` 块（例如 `output_provenance_schema` 附近）加：
```cpp
summary.Set("k2_export_probe", "k2-controlled-change-v1");
```
用独立 B-dev 先绑定基线再重建，保一行 diff，核新 BuildInfo/指纹/应用 exe，复验 exact2，按实际链接记录各组件 SHA。再按原合同在授权后用同平台同 seed S-A 运行到新 O-dev，观察真实 `[Values]` 键；纯科学 CSV 逐字节，scorer_statistics 只排除原合同两列 `run_wall_time_s`、`fom_per_s`，其余不放宽；执行 ID/时间/路径只登记。AR5 的 Windows 和 Linux 安装版各实际导出了原 S-A，在仓库外分别执行该摘要探针、恰两项组件测试及同输入 200 事件对照；各平台自身前后的 Dose/Fluence 逐字节相同，statistics 仅排除上述两列。Linux 两组件虽重链但不包含改动函数，其 SHA 保持；Windows SHA 差异不证明组件调用了该函数。见 [AR5 签收](collab/reviews/20261109-ar5-acceptance.md)。比较只覆盖该输入和冻结判据，不外推一般科学正确性。改后的 E-dev 预期被原 `verify_export` 拒绝，用基线 identity、精确 diff 和新编译/运行指纹标识开发树，不覆盖原 manifest。要发布新官方 export，回到已审查的开发候选，经模板重生成和正常入口发布到新 E；不能对旧导出清单手改授权。

## 迁移与回退

- **仓库组件迁移**：先迁唯一源归属和消费者链接，再迁头/配置/输出，按有限片提交。给旧接口保兼容入口或明确诊断；原 CMake 默认 standalone=OFF。区分应用真实组件和仓库专用 probe，别把开发目录、系统 SDK 路径或 Git 依赖塞进发布模板。模板成员变更重新生成、核新 digest；安装资源清单、干净源码快照和 SDK 源/依赖快照逐一核，不按旧数字补齐。
- **既有项目和数据**：保原项目/运行包/CSV；项目迁移用显式副本，保 schema、单位和输出含义。本候选支持的 UTF-8 BOM 输入保持原始来源字节，模板文本归一不是修改用户输入的理由。矩形导出只按当期白名单与支持矩阵；别用配置字段存在推断任意 GPS 可导。相空间 v1/v2 非离子仅按文档的 legacy 条件；含旧 ion/anti-ion（SDK 分类含 proton）需要从真实过程重录 v3，禁止改表头或编造状态。回退旧运行程序前核它真正能消费的 schema；保 v3 原件并另择兼容输入，不能把降级读取当可逆迁移。
- **源码或导出回退**：保失败原报告/原日志/源字节，从隔离工作树撤回有明确归属的切片或用已验上一发布的整套源码、模板、工具与 SDK 映射；新根重建和复核身份，不在共享 checkout 强制重置。E-dev 可精确恢复原字节后重新 verify，仍保失败和新输出；需要与旧发行交班时直接选原 E 及收据。不复用错 source 的 cache、不让已有产物覆盖失败、不改阈值/清单凑过。
- **安装回退**：只操作明确隔离的目标 prefix 和事务；按实际安装器的目录清单、`.g4usim-install.json`、事务 ID 和回执决定核验、恢复或卸载，先正常关闭所属进程；身份不确定就保现场，勿盲删、勿覆盖用户安装或试图手工拼装新旧 DLL/SDK。具体可恢复阶段、平台实物与过程收据由对应安装切片及主审最终冻结；本说明不替代候选实际安装和回退验收。

已执行范围以 [Roadmap](ROADMAP.md) 和阶段签收为准。Windows 一行可见修改的原件位于 `out/collab/20261108-ar0-ar6/independent/ar5-visible-edit-review`，主审逐字节回读位于 `ar5-primary-preparation/visible-edit-readback.json`；这些是本地证据路径，不是发布包的运行依赖。源码、模板和 SDK 版本变化后须按本说明建立新的候选证据。
