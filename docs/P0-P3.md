## P0：立即做，目标是“项目不误导用户”

这一阶段不追求新功能，只修正危险示例、文档和测试入口。

### P0.1 修正 `run_gdml.mac`

审计指出，`run_gdml.mac` 注释说不要 initialize，但实际包含 `/run/initialize`，这会让用户直接运行失败。GDML 当前只是 placeholder，没有 `G4GDMLParser` 后端。

建议：

```
1. 删除 run_gdml.mac 中的 /run/initialize 和 /run/beamOn；
2. 或把文件改名为 run_gdml_placeholder.mac；
3. 在 macro 顶部明确写：
   当前 GDML import 未接入 G4GDMLParser，不能运行初始化。
```

------

### P0.2 更新未实现功能说明

必须明确标注以下内容：

```
volume_fraction：预留，不能运行；
GDML：placeholder，不能 /run/initialize；
STL：未实现；
trap/trapezoid：parser only；
LET/Dose/Fluence：stub 或未验证；
/AIHL/output/...：未注册；
App/Detector messenger：源码存在但默认未注册；
多线程 CSV：当前不保证 race-free；
高级 biasing：future work。
```

这些结论都在审计报告中被列为 mismatch 或 avoid-for-now 项。

------

### P0.3 完成 XS biasing 验证计划

你刚完成 biasing XS 修改，所以现在应该补：

```
analog run
biased run
相同 geometry / source / physics / seed
比较 raw_edep、weighted_edep、process occurrence、hit weight
```

审计也明确写到：XS process-level biasing 是否确实改变目标 process occurrence，需要 analog vs biased run 对比验证。

建议新增：

```
macros/run_biasing_analog.mac
macros/run_biasing_process_level.mac
config/biasing/xs_process_bias.ini

```

## P1：近期优先实现，低风险且收益高

P1 是你接下来最适合让 Codex 逐个实现的阶段。

------

## P1.1 实现 `OutputMessenger`

审计判断 `OutputMessenger` 目前只是空类，不继承 `G4UImessenger`，也没有 `/AIHL/output/...` 命令。它被评为 P1 near-term implementation。

建议最小命令：

```
/AIHL/output/setDir <dir>
/AIHL/output/print
/AIHL/output/flush
/AIHL/output/close
/AIHL/output/setThreadSuffix <true|false>
```

不要在这里加：

```
/AIHL/output/enableHits
/AIHL/output/enableScoring
```

这些仍然归 `/AIHL/scoring/...` 管。

------

## P1.2 注册 `AppMessenger` 和 `DetectorMessenger`

审计指出：`AppMessenger` 和 `DetectorMessenger` 源码存在，但 `SimulationManager` / `main.cc` 没有实例化，因此默认运行时 `/AIHL/app/...` 和 `/AIHL/detector/...` 不可用。

建议：

```
AppMessenger：
    由 SimulationManager 持有；
    用于 /AIHL/app/printSummary、setVerbose 等轻量命令。

DetectorMessenger：
    由 DetectorConstruction 持有；
    用于 printRegistry、printSensitiveVolumes、printBiasVolumes、enableSD 等诊断命令。
```

注意：运行中修改 SD 状态不能简单生效，必须提示需要 `/run/reinitializeGeometry` 或重新初始化。

------

## P1.3 实现 `trap` / `trapezoid`

审计指出：`ParseShape()` 已经识别 `trap/trapezoid`，但 `VolumeBuilder` 没有创建 `G4Trap` 或 `G4Trd`，因此 parser 通过但运行失败。该项实现难度低、收益中等，被列为 P1。

建议分两种：

```
shape = trd
dx1 = 5 mm
dx2 = 10 mm
dy1 = 4 mm
dy2 = 8 mm
dz = 2 mm
```

和完整：

```
shape = trap
dz = 2 mm
theta = 0 deg
phi = 0 deg
dy1 = 4 mm
dx1 = 5 mm
dx2 = 6 mm
alpha1 = 0 deg
dy2 = 8 mm
dx3 = 7 mm
dx4 = 8 mm
alpha2 = 0 deg
```

短期建议先做 `G4Trd`，再做完整 `G4Trap`。

------

## P1.4 补齐 `layered_device` 的 `copyNo` 和 metadata

审计指出，`hierarchical` 能通过 unknown key 保存 `copyNo` 和 metadata，但 `layered_device` 只读取固定字段，不读取 `copyNo` 或任意 metadata；`VolumeBuilder` 已经能从 `userProperties["copyNo"]` 读取 copy number 并传给 `G4PVPlacement`。

建议最小实现：

```
LayeredDeviceTemplate：
    对每个 [layer.*]：
        读取 copyNo；
        保存 metadata.*；
        保存未知 key 到 userProperties；
        排除 thickness、xy、material、position、rotation、sensitive、bias、region、cuts、visual 等已知 key。
```

这对后续 hit 输出、层编号、器件阵列分析非常有价值。

------

## P1.5 多线程输出最小修复

审计认为这是 P1，而且是结果可信度问题。当前 `_t0` 后缀存在，但 `OutputManager` / `ScoringManager` 共享，`threadId` 固定为 0，多线程会有 race 风险。

我建议不要一步到位切到 `G4AnalysisManager`。先做：

```
方案 A：per-thread OutputManager + per-thread ScoringManager + 外部 merge
```

第一步目标：

```
1. 单线程保持完全兼容；
2. 多线程时每个 worker 写 *_tN.csv；
3. master 不直接写 worker event 数据；
4. run 结束后提示 merge 命令；
5. 暂不自动 merge。
```

这比加锁写单文件更安全，也更容易调试。

# 四、P2：中期核心能力

P2 不建议现在立刻全部做，但应该作为下一轮开发主线。

------

## P2.1 `volume_fraction`

审计判断：parser 已经识别，但 `MaterialFactory` 后端明确抛异常。实现可行，但不能把体积分数误当质量分数。

建议实现规则：

```
仅允许 component 是 material；
用 rho_mix = sum(v_i * rho_i)；
用 w_i = v_i * rho_i / rho_mix；
最后调用 AddMaterial(subMaterial, w_i)。
```

不要允许元素直接使用 `volume_fraction`，除非提供显式密度。

------

## P2.2 GDML world replacement

审计认为 GDML 是 medium-term core feature，比 STL 更值得做。当前 `GDMLTemplate` 只是 placeholder，`VolumeBuilder` 会抛异常。

我建议不要把 GDML 塞进 `VolumeBuilder`，而是走：

```
DetectorConstruction::Construct()
    if geometry mode == gdml:
        G4GDMLParser parser;
        parser.Read(file);
        world = parser.GetWorldVolume();
        GeometryRegistry 从 LogicalVolumeStore / PhysicalVolumeStore 注册名称；
        sensitive_volumes / bias_volumes 根据名称标记；
        return world;
```

这比把 GDML 转成 `VolumeNode` 更稳。

------

## P2.3 DoseScorer / FluenceScorer

审计指出：`DoseScorer` 和 `FluenceScorer` 当前是 no-op，`LETScorer` 只是读取未填充的 `LETcalc` 字段。

建议优先级：

```
先 Dose
再 Fluence
最后 LET
```

Dose 最小定义：

```
dose = weighted_edep / mass
```

需要 volume mass。第一版可以只支持：

```
每个 logical volume 的 total dose
```

Fluence 先明确为：

```
track-length fluence = sum(stepLength * weight) / volume
```

不要直接叫“fluence”而不说明定义。

LET 先不要做真实实现，先写 `docs/LET_DEFINITION.md`。

# 八、最终建议

你现在最应该做的不是继续写新大模块，而是把项目从：

```
功能很多，但部分是 placeholder/stub/parser-only
```

推进到：

```
用户看到的功能都能真实运行；
不能运行的功能明确标注；
单线程输出可信；
biasing 有 analog 对照验证；
多线程至少不会损坏输出。
```

推荐下一步从 **P0 + P1** 开始：

```
1. 修正文档和危险 macro；
2. 实现 OutputMessenger；
3. 注册 AppMessenger / DetectorMessenger；
4. 实现 trd/trap；
5. 补 layered_device copyNo/metadata；
6. 设计并修复 per-thread 输出。
```

这条路线最稳，也最符合当前审计报告的结论。
