## 问题 2 元数据写失败留下成功摘要

分类：已复现程序缺陷；优先级 P2。用户同意按此前意见记录。状态：待修复。

### 位置和原因

- `SimulationManager.cc:639-649` 先把文本摘要及元数据加入生成文件清单、设置完成标志，再写文本摘要，最后写元数据。
- `OutputManager.cc:171-174` 将元数据写入交给 RunSummary。
- `RunSummary.cc:284-289` 在无法打开元数据文件时抛出异常。
- `main.cc:954-964` 和 `993-1004` 的 finalizationStarted 使元数据写失败后不再更新已发布的文本摘要。

### 复现方法和实际观察

1. 准备独立输出目录，在其中预先创建名为 `run_metadata.json` 的目录。
2. 使用有效配置，单线程执行 `/run/initialize` 和 `/run/beamOn 1`。
3. 检查进程退出状态、`run_summary.txt`、元数据目标类型和生成文件清单。

实测单次约 1.4 秒，完成事件数为 1。元数据无法打开，实际进程退出 1；stderr 报告 `Failed to open run metadata file`。但文本摘要仍为：

```text
status = completed
program_exit_code = 0
summary_write_status = completed
output_failure_status = none
```

生成文件清单还包含实际为目录的 `run_metadata.json`，schema 标记为 `run_metadata_json_v1`。

对应证据：临时目录下 `metadata_collision.stderr.log`、`metadata_collision/run_summary.txt` 和 `results.json` 的 metadata_collision 实例。此测试使用真实文件名冲突，没有设置输出故障注入变量。

### 影响及推荐修复

进程状态与落盘证据矛盾；只读取摘要的离线流程可能误判交付完整。依赖真实进程非零退出码的 GUI 能判失败；本轮未证明场景分析器会接受该目录，也不据此认定模拟数值错误。

建议：将元数据写出失败纳入收尾错误登记；尽力将可写的文本摘要更新为失败并记录实际退出码及失败阶段；生成文件登记必须符合实际写出结果，不能将未生成的元数据冒充成功文件。可提前检查目标冲突，但不能以预检替代写出阶段的异常处理。

修复后应回归：正常写出、元数据目标被目录占用、元数据写入或关闭失败，以及文本摘要仍可写时的失败回写；核对退出码、摘要状态、错误阶段和生成文件清单一致。不得只证明退出码非零。
