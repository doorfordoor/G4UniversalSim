# 项目协作模型分配

决定日期：2026-10-31。用户要求按任务范围、能力与消耗分配模型，替代所有子任务继承 Astra/最高推理档的做法。正在运行的子任务先完成并交接；下一份独立任务再选模型，不重启已经完成的实现或验证。主负责人统一接口、验收和提交，继续保留独立审查。

## 分派规则

| 模型 | 项目中的主要任务 | 默认推理与升级 |
| --- | --- | --- |
| GPT-6 Astra | 架构与跨模块契约、物理定义/统计口径、关键缺陷裁决、困难复审 | 常规裁决用可用的 Light/Medium；跨模块或科研问题再用 High/Extra High。Max/Ultra 按具体困难启用，不向所有子任务继承 |
| GPT-6.1 Sol | 默认开发者；C++/Python/PySide6实现、事务/线程/异常路径、常规独立代码审查 | 边界明确用 Medium；复杂状态/并发/多模块用 High。有依据的疑难升级 Astra |
| GPT-6.1 Terra | 截图/界面层次、实际窗口观察、易懂中文、设计稿和文档审查 | 默认或 Medium；视觉结论仍要实际查看图像，不能代替运行证据 |
| GPT-6 Sol | 已有任务连续性、6.1 Sol不可用时的兼容备选 | Medium/High按范围；不为省额度而强行占一个角色，标准输入/输出计价并不低于6.1 Sol |
| GPT-6 Luna | 明确规则的提取、清单/文档一致性检查、窄测试夹具、小型重复改动 | High起步，限定输入/输出/文件；不独立决定物理公式、并发架构或阶段关闭 |
| DeepSeek | 前端视觉方案、获分配的前端实现与文案 | 延续既有职责；交付走相同源码/测试/实窗审查，不把设计回信等同实现完成 |

官方将 6.1 Sol 定位为较低消耗的复杂持续工作选择，Terra 侧重写作/视觉/应用操作，Luna 侧重明确、重复任务；建议从默认推理开始，普通任务通常不需要 Max/Ultra。[模型说明](https://learn.chatgpt.com/docs/models)

实际调用的速度档和服务路由可能不同；上表不能直接换算本轮费用，也不承诺某个固定节省比例。

## 调度与质量约束

1. 常规用一名实现者和一名独立审查者；确有互不重叠的工作才并行。能由脚本精确比较的摘要、成员、计数和状态交给工具，模型处理差异与结论。
2. 新任务给简短交接：目标、已定契约、允许文件、证据路径、验收标准。已有大对话不整段复制给每个执行者；同一文件始终一个写者。
3. 升级依据是可复现的困难、两次不同修复仍失败、审查分歧或科学假定未定；排队、下载、已知命令等待不需要升级。升级只传失败证据和相关源码。
4. 分配时记录实际模型和推理档；无法取得真实token/费用就写未知，不杜撰。较低成本模型通过既定验收后，不因模型名称额外重做一遍全部工作；高风险模块仍保留独立主审。
5. 当前协作接口明确支持 `gpt-6.1-sol` 和 `chatgpt-web/gpt-6-sol` 等已列选项，但尚未暴露可选的 Terra/Luna。角色计划不等于已实际调用；可用前由6.1 Sol适当档位承担，并明确记账。不能猜别名或把其他模型标成Terra/Luna/Astra。不可原地切换的旧agent在其任务结束后交接给新agent。

F5期间的首个实际调整：`f5_delivery_sol` 使用 `gpt-6.1-sol`、`medium`、新上下文，只负责收尾文档准备；正在运行的CI任务保留原上下文完成。后续阶段沿本规则分派，Astra仍承担必要的总设计与首席审查职责。
