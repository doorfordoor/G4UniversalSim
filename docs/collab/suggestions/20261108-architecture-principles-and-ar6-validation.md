# AR0–AR6补充建议：依赖方向、分层约束与实际扩展验收

2026-11-08，来自用户要求的架构原则评估补充。供新主审纳入现有AR0–AR6规划及MR1/MR2/MR3复盘；不是新的功能阶段。本建议由旧审计对话编写，新主审负责与当前冻结合同对照、说明采纳位置并维护最终规划。

## 1. 评价目标与适用边界

合格目标是修改影响范围更小、状态与失败可追踪、局部逻辑可独立验证。拆文件、增加接口数量、减少dynamic_cast或全部测试通过，都不能单独证明架构合格。

现有AR0及AR1已签收部分和在途冻结候选保持原身份。把本建议映射到尚未实施的切片与既有复盘出口；优先复用已有证据，不为补充原则重新执行原K2全矩阵或打断正常任务。发现确实违反原功能正确性的反例，沿既有最小修复规则单列；其余在对应架构阶段完成。

## 2. 建议明确的依赖方向

这里约束的是源码/模块依赖，不是数据流先后图。运行数据可以经端口返回，不能据此反向导入具体UI或基础设施。

|边界|建议允许的依赖|需要阻止或显式说明的依赖|
|---|---|---|
|输入适配与GUI控制器|调用领域描述、校验/事务及应用服务合同|窗口组件作为后端规则的唯一真相；消费者各自重写配置语义|
|领域描述与规则|值类型、稳定能力描述及必要数学/物理定义|QWidget、QProcess、活动writer、worker累计器及文件发布实现混入描述|
|应用编排/会话|领域描述及稳定的执行、输出、取消、结果证据合同|导入具体窗口；复制内置scorer/shape的分支规则；自行猜测输出文件即成功|
|Geant4及文件/进程适配|实现上述合同，管理真实对象和资源生命周期|基础设施反向调用窗口业务；将跨线程可变对象塞回共享描述|
|装配入口|选定实现并完成注入/登记|让每个消费者自行创建和选择实现，形成隐藏服务定位器|

计分、场和几何构造本来属于Geant4引擎实现，允许明确依赖Geant4；不要求把内核全部封装成平台无关框架。重点是使可独立处理的描述、编辑状态和编排规则不受无关具体实现牵制。

## 3. 依赖倒置与所有权建议

1. 在真正会变化的边界定义最小稳定合同，如scorer工厂、执行/取消、输出发布、运行结果判定。由使用方需求决定合同，具体实现经装配入口提供。C++虚接口、可调用对象、Python协议或已有服务均可，不要求每个类增设接口。
2. 工厂只有在消费者依赖合同、无需知道全部内置类型时才改善依赖方向；中央switch改名成Factory但不断增分支，不视为已证明扩展性。
3. 描述/Spec不可变，累计器与writer按worker/run拥有；提交模型、草稿、展示状态、历史运行证据分别说明所有者、寿命和失效条件。兼容适配器标记读写者和退出条件，不维持两套权威状态。
4. 异常、取消和输出发布通过稳定结果合同传递。共享“成功判定”，避免历史/扫描/分析器各自推断。发布成功后的清理异常与发布失败分开表达。
5. 通过CMake target依赖、少量针对性导入/包含检查及无UI测试约束已迁移边界。检查要覆盖真实反向依赖和循环，而非仅检查目录名或类名。临时例外写明原因、涉及消费者、处理阶段。

## 4. 实际扩展验证：复用既有切片，不另造功能

|验证|建议操作与证据|架构判断|
|---|---|---|
|scorer扩展|复用AR2唯一确定性测试scorer。记录涉及实现、登记、测试及构建文件，验证sequential与原1/2/4 worker、两run隔离/失败负控|新增同类scorer无需改main或中央内置类型判定；必须修改时说明真实公共契约原因|
|编辑字段迁移|从AR4本来迁移的run/path/source等字段中选代表项；无QWidget完成编辑/序列化/恢复，再接窗口适配与Undo/raw草稿回归|领域规则无需修改无关页面；模型是权威数据，兼容投影不是第二个数据源|
|基础设施替代|在已有输出发布或执行失败测试中使用测试替身/故障注入，观察应用层成功、失败、取消及清理合同|替换实现无需改领域计算；不能用仅模拟调用次数的测试代替真实适配器集成验证|
|构建与消费者|AR5比较原生/组件/K2导出的共同源码和target依赖，复用原子集及闭包验收|局部变化的消费者和验证范围可解释，导出器不另立与后端相冲突的支持判定|

每例记录修改前/后涉及的模块、中央分支、公开接口和必要测试；给出具体diff与调用关系。模块数量并非越少越好，不设任意“最多修改N个文件”或加速百分比门槛。必要的显式接线变化可接受，跨层规则重复及无关模块改动要解释。

## 5. 阶段落点与AR6签收建议

- AR0：以已冻结接口表为底稿，补可检验依赖方向/例外清单；属于后续澄清，不覆写旧签收。MR1前确认AR1/2新增抽象是否确实收敛影响。
- AR1/AR2：沿当前几何事务、描述/工厂与线程所有权切片执行；scorer扩展证据直接复用原定测试。
- AR3：落地应用编排、执行/取消和统一失败/证据合同；装配入口集中选择具体实现。
- AR4：落实无控件编辑状态及窗口适配；选一个既有迁移字段验证修改影响。
- AR5：落实构建依赖与共同源码所有权，固定可执行的依赖检查及例外。
- AR6/MR3：合并阶段证据，提交简洁依赖图（注明这是源码依赖）、边界规则/例外表、三个代表性扩展实例、所有权/失败合同和原正式回归/科学比较结果。分别判定“行为正确”“架构边界成立”“扩展修改范围改善”，不能互相替代。

AR6报告至少回答：是否有未解释的反向/循环依赖；代表性扩展是否还要修改无关中央模块；核心规则是否可脱离窗口验证；替换实现是否牵动领域计算；旧适配和限制是否有明确归属。未满足项写出具体反例、影响与处理决定，不用“已分层/已解耦”概括通过。源码/构建产物和测试身份继续按现行证据门禁绑定。

本建议不恢复DS/web、不追加F3测量、不提高科学适用域，也不要求重建通用插件/依赖注入框架。用户本次授权的是整理与交付补充建议；具体纳入既有阶段清单由新主审在对照后记录。
