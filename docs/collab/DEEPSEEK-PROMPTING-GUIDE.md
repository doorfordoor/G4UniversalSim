# DeepSeek Harness V4.1 Flash 指令指南

适用：现有桌面会话、codex-dsh-collab 0.2.0、deepseek-flash / Max。首轮写完整任务，执行中追加只写变化；目标、具体证据和下一动作放在前面，鼓励保持简短。任务里的工程限制按实际风险添加，不套用大段通用禁令。

以下区分官方支持机制与本项目的实践建议；没有进行提示词效果的对照实验，不宣称某种写法必然提高准确率或提速多少。

## 模型与发送机制

官方将V4.1 Flash的API模型名列为deepseek-flash；Max由实际模型参数reasoning_effort=max控制，不靠提示词中写“Max模式”开启。当前桥把provider/model/reasoningEffort放在请求字段，实际运行配置须看observedConfig。官方说明见[发布说明](https://www.deepseek.com/en/news/deepseek-v4-1-flash/)和[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)。

思考模式下temperature参数被忽略；不把旧R1的温度、禁止system消息、手写think前缀等经验直接套进当前Harness。模型编码和工具协议交给已安装运行环境，不在普通任务消息里拼装控制标记。当前官方API指南与开源权重的本地推理采样参数针对不同运行方式，不混用。

| 情况 | 发送方式 | 指令重点 |
| --- | --- | --- |
| 空闲时开始新任务 | queue | 完整目标、输入、范围、完成标准 |
| 当前工作结束后的下一项 | queue | 接续关系及下一项交付 |
| 执行中修正方向或补关键事实 | steer | 当前任务锚点、新证据、明确修改及下一动作 |
| 发现会损坏数据或使结果错误的操作 | steer | 明确暂停相关操作，保存现场后修正；文字不等于已经取消原进程 |
| 完成交付后返回修复意见 | 空闲时queue | 原候选、反例、修复范围和复验条件 |

Queue进入后续轮次，Steer进入后续执行步骤；Steer不是立即中断当前工具，也不是撤销已执行动作。Bridge的kind=review/feedback只是消息类别，不能替代mode。当前桥没有公开inject操作，不因为官方Agent API有inject就猜一个HTTP接口。机制见[官方Agent文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/agent/README.md)与[桥协议](https://github.com/ESROAMER/codex-dsh-collab/blob/main/PROTOCOL.md)。

桌面手动发送的Enter行为受设置控制，发送前看按钮显示Queue还是Steer；Ctrl+Enter采用相反的发送方式。自动派工直接指定mode，不依赖界面默认值。[官方输入框说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-conversation/README.md)

接纳回执只证明消息已接纳。通过原任务的增量事件确认开始处理、实际采用模型、最终交付；不以一句“收到”代替落实。网络结果不明时先查原请求，重试保持同一requestId和正文。

## 首轮任务写法

首轮一般包含六项：任务目标、当前起点、必要材料、可写范围、完成标准、交付方式。复杂阶段可以写完整阶段目标及内部节点，不要求每个内部节点都等待下一条指令。优先给可观察的行为要求，让实现方式有选择空间；只有架构已经确定时才规定接口或实现。

推荐模板：

```text
执行 <任务ID>：完成 <阶段或功能>。

目标：<完成后的可观察行为>。
当前起点：<候选/已完成部分/唯一未决点>。
只需读取：<当前清单和关键文件>。其余材料在实现需要时再查。
修改范围：<模块或文件>。

完成标准：
1. <正常路径的具体结果>。
2. <本任务必要的失败或边界行为>。
3. <相关测试、实际操作或数据对照>。

自主完成实现、相关验证和修复，推进到上述范围完成。
交付：<实际改动、验证结果、证据路径、剩余问题>。
完成后冻结改动待复验。

请有信心做出完整、清晰、美观、快速、易用的成果。
unlimited Token，不限子智能体数量；按任务需要组织工作，充分实现和验证。
```

对低风险小改动，目标加完成标准即可，不机械填满模板。协议、配置写回和物理结果相关任务，补上必要的不变量、输入/输出身份和原始失败保留；不把这些约束无差别复制到每个文案任务。

## 执行中追加指令

追加采用“继续哪个任务→新增了什么→具体改什么→接下来做什么”。不重发旧任务全文，不用“再仔细一点”“继续优化”代替技术信息。需要替换旧要求时，明确写“替换第几项”，避免两条冲突要求同时留在上下文。

推荐模板：

```text
继续 <任务ID>，本条补充 <具体问题>。

新证据：<实际现象、输入、输出及证据位置>。
定位：<文件:行号，或待验证的具体假设>。
调整：<需要改变的行为或技术决策>。
完成条件：<怎样证实调整有效>。

其余目标和范围沿用原任务。当前相关命令仍在运行时先跟进原进程；
完成这一修正后回到原清单继续，不另开前置工具项目。
```

同一问题的紧密关联证据合并为一次追加；紧急的结果错误及时Steer，普通优化留到交付后或后续任务。需要的输出是关键判断和实测依据，不是反复要求长篇自述推理。

本项目例子：第一轮已完成5/5且phase=ready，但输入框禁用，无法修改下一轮；指定session_panel.py的ready and not run，把留存完成轮错误当作运行标志；要求按真实phase和编辑资格启用，并在真实流程中断言isEnabled。它比“完善会话交互”更容易直接执行。

## 交付后的修复回信

```text
<任务ID> 在 <候选> 的复验发现 <具体失败>。
复现：<最短步骤或命令>。
实际：<观察到的行为>。
应有：<原定完成标准>。
证据：<文件路径或原始日志>。

修复 <最小相关文件范围>，补充能失败于旧实现的回归，验证正常路径仍成立。
保留原失败报告；完成后提交本次改动清单和新证据路径，冻结待复验。
unlimited Token，按需要充分定位、修复与验证。
```

反例可直接执行时优先给反例；根因未确定就写“假设”，不把猜测强制变成实现。环境、测试接线与产品缺陷分别定位。本项目中smoke_session_backend忽略G4USIM_EXE，应修测试绑定而非改产品默认路径或放宽超时。

## 卡住时怎样指导

给一条可检验的判断及最小试验，例如：“先核对原进程是否仍在跑，读取最后一个新日志和退出事实；若已结束，依据首个失败点修复。”不要笼统重复“继续尝试”。同一种方法两次确实失败后，换方法或说明缺失条件；正常等待不算失败。

性能任务先写操作、条件与测量口径，例如冷启动/热启动、相同配置、真实窗口响应；再决定修哪里。前端设计写清信息层级、主要操作、参考图和允许自主发挥的范围，不逐像素规定实现。

前端追加示例：“保持现有功能和导航入口，增强配置、结果、运行状态三个区域的区分。主要操作突出，次要信息收敛；优先通过布局、留白、明暗和字号层级完成，按你的审美自主设计。交付实际界面及代表性截图，并检查窄窗口中的主要操作可达。”

## 长上下文与鼓励语

保持稳定背景，后面追加具体变化；这也符合官方前缀缓存机制，但缓存命中不代表模型必然记得每个旧决定。[官方上下文缓存](https://api-docs.deepseek.com/guides/kv_cache/)

当前状态保存在CURRENT-SUPERVISION.md；任务正文指向当前清单。只有缺项或冲突才回查旧材料。上下文需要整理时保留目标、已定决策、修改文件、运行进程、未决失败和下一动作，不重放全部旧聊天。

鼓励语可以保留，自主决策空间也应明确。unlimited表达工作预算取向，不能替代服务实际配额或真正的Max设置；没有找到“声称来自某公司”能稳定改善V4.1 Flash的官方依据。后续指令直接写目标和动作，不提提出者、实现者身份，也不添加全知全能的人设。

任务完成程度、返工轮数、实际耗时和复验结果可从现有回执持续比较，逐步调整模板；无需为提示词另建一套验收平台。
