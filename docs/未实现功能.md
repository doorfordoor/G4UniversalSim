   # G4UniversalSim 当前实现限制与已知问题整理

   根据当前源码和配置文件实现，项目中存在若干“接口已预留但功能未完整实现”的情况。部分功能在配置文件、README 或 Messenger 中已经出现，但实际运行时并不能可靠使用。需要在文档中明确标注，或在后续开发中补齐实现。

   ## 1. 材料模块：`volume_fraction` 模式尚未实现

   当前材料配置中支持解析：

   ```ini
   mode = volume_fraction
   ```

   parser 层可以识别该字段，但 `MaterialFactory` 中尚未实现体积分数混合材料的构建逻辑。运行时会抛出类似错误：

   ```text
   volume_fraction mode is reserved but not implemented
   ```

   因此，`volume_fraction` 当前属于**预留功能**，不能作为可运行配置使用。

   目前可用的材料配置应仅限于源码中已经真正实现的模式，例如基础材料、元素质量分数混合等。文档中不应把 `volume_fraction` 描述为已支持功能，除非明确标注为：

   ```text
   Reserved / planned / not implemented yet
   ```

   ------

   ## 2. GDML 输入：配置存在，但真实导入未完成

   当前存在 GDML 配置示例，例如：

   ```ini
   [gdml]
   file = geometry/model.gdml
   world_name = world
   sensitive_volumes = SV1, SV2
   bias_volumes = Shield1
   ```

   但根据当前实现，`GDMLTemplate` 只是创建 placeholder 类型的 `VolumeNode`，并没有真正调用 Geant4 的：

   ```cpp
   G4GDMLParser
   ```

   也就是说，目前 GDML 配置更接近**占位接口 / 实验性接口**，并不能完成真实的 GDML 几何导入。

   当前问题包括：

   ```text
   1. GDMLTemplate 只生成占位 VolumeNode；
   2. VolumeBuilder 未调用 G4GDMLParser；
   3. gdml 文件中的真实 world、daughter volumes、材料、solid 等不会被实际导入；
   4. sensitive_volumes / bias_volumes 即使被解析，也未必能映射到真实 GDML 体积；
   5. 文档若描述为“已支持 GDML 导入”，需要修正。
   ```

   建议文档中描述为：

   ```text
   GDML import is currently experimental and not fully implemented.
   The current GDMLTemplate creates a placeholder geometry node only.
   Real G4GDMLParser-based import is not yet wired into VolumeBuilder / DetectorConstruction.
   ```

   ------

   ## 3. STL 输入：目前只是规划功能

   STL 输入目前属于规划功能，当前没有完整 parser、template、VolumeBuilder 接入或 Geant4 solid 构建流程。

   因此，当前项目不应宣称已经支持：

   ```text
   STL import
   mesh import
   STL-based geometry construction
   ```

   除非后续明确实现了类似：

   ```cpp
   G4TessellatedSolid
   ```

   或其他 mesh-to-solid 构建逻辑。

   文档中建议标注为：

   ```text
   STL import is planned but no stable user-facing interface exists yet.
   ```

   ------

   ## 4. Scoring 模块中部分 scorer 仍是 Stub

   以下 scorer 当前可能已有类、接口或配置入口，但真实物理计算尚未完整实现：

   ```text
   LETScorer
   DoseScorer
   FluenceScorer
   ```

   这些 scorer 如果只是返回占位值、空结果或简单统计，就不能在文档中描述为“完整 LET / dose / fluence 物理 scoring”。

   应区分：

   ```text
   1. scoring framework exists；
   2. scorer interface exists；
   3. real physics calculation implemented；
   4. validated result output available。
   ```

   当前更准确的描述应是：

   ```text
   The scoring framework is partially available, but LETScorer, DoseScorer and FluenceScorer require further implementation and validation.
   ```

   ------

   ## 5. ParticleAggregator / 粒子分组高级分析尚未完整实现

   `ParticleAggregator` 或类似粒子分组分析功能目前属于高级分析规划项，尚未形成完整、稳定、可验证的输出链路。

   如果 README 或命令文档中出现：

   ```text
   particle grouping
   advanced particle aggregation
   per-particle-family analysis
   ```

   需要标注为未完成或实验性功能。

   ------

   ## 6. 多线程输出与自动 merge 尚未完全实现

   当前 `OutputManager` 不保证线程安全。

   现阶段设计更倾向于：

   ```text
   每个 worker 线程独立输出文件
   ```

   例如：

   ```text
   output_t0.csv
   output_t1.csv
   output_t2.csv
   ```

   然后再通过：

   ```text
   merge_outputs.py
   mergeHistograms
   ```

   进行后处理合并。

   因此，当前不能假设多个 worker 可以安全写入同一个输出文件。文档中也不应暗示：

   ```text
   multi-thread output is automatically merged
   ```

   更准确的描述是：

   ```text
   Multi-threaded output is currently expected to use per-thread output files.
   Automatic thread-safe merging is not fully implemented.
   Use merge_outputs.py or mergeHistograms as a post-processing step.
   ```

   ------

   ## 7. Geometry 模块：`trap` / `trapezoid` 只被解析，未真正构建

   当前 `ParseShape()` 可以识别：

   ```text
   trap
   trapezoid
   ```

   但 `VolumeBuilder` 中尚未实现对应的 `G4Trap` 构建逻辑。

   因此，如果配置文件中使用：

   ```ini
   shape = trap
   ```

   或：

   ```ini
   shape = trapezoid
   ```

   解析阶段可能通过，但几何构建阶段会失败。

   该功能当前属于：

   ```text
   parser recognized but builder not implemented
   ```

   建议文档中明确标注：

   ```text
   trap / trapezoid shapes are reserved. They are parsed but not yet supported by VolumeBuilder.
   Do not use them in runnable geometry configs.
   ```

   ## 8. QT UI 界面尚未形成可用功能

   如果项目中已有 QT UI 相关规划、目录、README 描述或占位代码，目前也应视为未完整实现功能。

   需要确认以下内容是否真实存在：

   ```text
   1. 是否有可编译的 Qt target；
   2. 是否接入 SimulationManager；
   3. 是否能加载 config / macro；
   4. 是否能控制 run / geometry reinitialize；
   5. 是否能显示输出或状态。
   ```

   在未确认前，文档中不应把 QT UI 写成已支持功能。建议标注为：

   ```text
   Qt UI is planned / experimental and not part of the default executable workflow.
   ```

   ```text
   /AIHL/output/...
   ```

   伪命令。

   ```text
   Output configuration is currently controlled mainly through config files or manager initialization.
   The OutputMessenger command interface is not implemented yet.
   ```

   ## 10. 部分高级 biasing 功能只有文档缺口，没有 parser 或 messenger

   以下功能目前不能视为可用：

   ```text
   importance biasing
   weight-window
   splitting
   Russian roulette
   ```

   当前问题是：

   ```text
   1. 没有稳定 parser；
   2. 没有 messenger 命令；
   3. 没有 manager-level 可运行实现；
   4. README 可能只是记录未来扩展方向。
   ```

   因此，文档中应避免把这些功能列入“当前支持命令”或“当前可运行配置”。

   建议标注为：

   ```text
   Advanced biasing methods such as importance biasing, weight-window, splitting and Russian roulette are documented as future work only.
   They are not currently available through parser or messenger interfaces.
   ```

   ------

   ## 11. `layered_device` 模板不消费 copy number / metadata

   当前 `layered_device` 模板没有写入或消费：

   ```text
   copy number
   metadata
   ```

   这些字段目前主要存在于 `hierarchical` 的通用 geometry parser 中。

   因此，测试配置或文档中需要区分：

   ```text
   layered_device:
     主要用于层状结构快速构建；
     不应假设支持完整 metadata/copy-number 语义。
   
   hierarchical:
     更适合测试通用 geometry node；
     可以覆盖 metadata / copy number 等字段。
   ```

   如果要测试 copy number / metadata，应优先放在 `hierarchical` geometry 配置中，而不是 `layered_device`。

   ------

   ## 12. `AppMessenger` 和 `DetectorMessenger` 有源码命令，但默认 executable 未必注册

   源码中存在：

   ```text
   /AIHL/app/...
   /AIHL/detector/...
   ```

   相关命令定义，但当前默认 executable 中，`SimulationManager` 或 `main.cc` 未必实例化并注册：

   ```cpp
   AppMessenger
   DetectorMessenger
   ```

   因此这些命令是否在运行时可用是不确定的。

   如果英文文档中暗示这些命令默认可用，需要修正。更准确的表述是：

   ```text
   AppMessenger and DetectorMessenger define /AIHL/app/... and /AIHL/detector/... commands in source code, but they are not guaranteed to be registered by the default executable unless explicitly instantiated and wired into SimulationManager or main.cc.
   ```

   后续需要检查：

   ```text
   1. main.cc 是否创建 AppMessenger / DetectorMessenger；
   2. SimulationManager 是否持有它们；
   3. 它们的生命周期是否覆盖整个 Geant4 UI session；
   4. 命令是否能通过 /control/manual 或 macro 实际看到。
   ```

   # 建议后续处理方式

   我建议把这些问题分成三类处理。

   ## A. 文档立即修正类

   这些不一定需要马上写代码，但必须避免误导用户：

   ```text
   volume_fraction
   GDML import
   STL import
   trap / trapezoid
   OutputMessenger
   advanced biasing
   Qt UI
   multi-thread auto merge
   ```

   文档中应统一使用：

   ```text
   Implemented
   Partially implemented
   Reserved
   Experimental
   Planned
   Not implemented
   ```

   这几个状态，而不是笼统写“支持”。

   ## B. 测试配置需要避开类

   当前测试配置中不要使用：

   ```text
   mode = volume_fraction
   shape = trap
   shape = trapezoid
   gdml import
   stl import
   /AIHL/output/...
   importance / weight-window / splitting / Russian roulette
   ```

   否则测试会失败，且失败原因不是配置错误，而是功能本身未实现。

   ## C. 后续源码补齐类

   如果要继续完善项目，建议优先级为：

   ```text
   1. 修正文档与命令说明，区分 implemented / planned；
   2. 注册或移除 AppMessenger / DetectorMessenger 的默认文档描述；
   3. 实现 OutputMessenger 或从文档中暂时移除 /AIHL/output/...；
   4. 实现 VolumeBuilder::CreateTrapSolid；
   5. 实现 MaterialFactory 的 volume_fraction；
   6. 实现真实 GDML import；
   7. 实现多线程输出 merge；
   8. 实现真实 LET / Dose / Fluence scorer；
   9. 再考虑 STL import 和 Qt UI。
   ```

   最核心的问题可以概括为一句话：

   > 当前项目中存在多处“配置/接口/文档已出现，但运行实现尚未完成”的功能，需要在文档、测试配置和源码接入三方面统一口径，否则会导致用户以为功能可用，但实际运行失败。
