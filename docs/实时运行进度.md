# 实时运行进度（F6）

Run Console 接收后端标准输出中的版本化进度，显示当前 run 的已处理/计划事件数、平均速率和预计剩余时间。初始化与未收到消息时显示未知；旧后端仍可运行，不因没有进度而改变成功判定。

## 协议与含义

每条消息以 `[G4USimProgress] ` 开始，后跟一行 JSON，结束换行并刷新标准输出。例如：

```json
{"schema":"g4usim_progress_v1","run_id":0,"sequence":12,"phase":"running","planned_events":1000,"completed_events":400,"elapsed_s":2.0,"rate_eps":200.0,"eta_s":3.0}
```

| 字段 | 含义 |
| --- | --- |
| schema | 固定版本 g4usim_progress_v1，GUI 忽略不兼容版本 |
| run_id | Geant4 run ID，每轮独立统计 |
| sequence | 可选的进程级单调序号；后端每次写消息自增，跨 run 不重置。GUI 用它拒绝重复或乱序的行；旧后端不写该字段时按旧行为接受 |
| phase | begin 开始、running 进行、end 本轮结束、aborted 本轮中止或发生输出失败 |
| planned_events | 本轮计划事件数 |
| completed_events | 事件处理计数；中间值为已经完成 EndOfEventAction 中计分收尾的数量，末条以 master 合并后的 G4Run::GetNumberOfEvent() 为准 |
| elapsed_s | 本轮 BeginOfRunAction 起的单调时钟秒数，包含本轮准备与收尾 |
| rate_eps | 累计处理计数/累计秒数；无法估计时为 null |
| eta_s | running 时按平均速率估算剩余事件耗时；无法估计或 aborted 时为 null；完整 end 为 0 |

数字必须有限且非负。GUI 也允许计划数/完成数/耗时为 null 表示未知，不从宏文本猜测计数。planned_events 为零或未知时不显示百分比。`/run/beamOn 0` 可能不进入 Geant4 run 回调，因此没有 begin/end 消息是正常的。

中间计数包含到达事件收尾的 aborted event，不是“物理有效事件数”。终值直接使用现有摘要的处理数口径；它不证明所有物理历史完整。事件数达到计划数但尚未收到终消息时，GUI 显示收尾中。

ETA 仅估算剩余事件处理，不能预测初始化、写出合并、后续 run 或最终进程结束时间；不同事件复杂度、输出负载和初期采样都会影响估计。

sequence 是进程级计数，第一个 run 从 1 开始连续递增，跨 run 不重置，因此同一进程内第二轮的首条消息一定大于第一轮的终消息。GUI 只把它当作顺序证据：缺失时保持旧行为，出现时必须是非负整数且严格递增，否则丢弃该行（不判失败、不改最终结果判定）。它不替代 run_id 与计数校验，也不证明物理历史完整。

## 生命周期与失败

master/sequential 在本轮准备之前发 begin，worker 不重置共享计数；worker/sequential 在计分事件收尾之后原子递增。running 消息在所有线程间合计最多约每 0.5 秒一条，begin/终消息不受此限制。全部 worker 收尾后，master 完成该轮输出处理再发 end/aborted。进度使用单次标准输出写入，避免 Geant4 worker 前缀；普通日志仍保留。

`end` 只表示本轮回调结束，不表示整个进程成功。其后的主线程最终 Flush/Close 仍可能失败。GUI 最终结果继续由 `run_result.py` 根据退出情况与本次新摘要判定；进度条不是验收依据。

用户停止/强杀时 GUI 立即保留最后观察值并在状态文字显示终态（结果：用户停止／强制结束），不再输出“进度已冻结”。强杀、崩溃及断连可能没有终消息，不补造完成事件；进程退出后提示查看最终结果。停止请求遵循原有 QProcess 语义，不能保证 Windows 控制台进程响应 terminate，必要时仍需强制结束。

进度解析支持 UTF-8 分块、JSON 跨读取块、普通日志前缀及正常 EOF 尾段。拒绝坏 JSON、未知版本、非有限/越界值、旧 run、同轮倒退计数/时间、重复或回退的 sequence 与终消息后的继续更新；单行缓冲限制 16 KiB，超长行丢弃到下一换行。损坏消息不会让模拟被判成功。

## 性能与支持边界

没有新增 INI、CLI 或 macro 配置；真实运行自动输出进度，不更改源、物理列表、随机数、计分公式、文件命名或摘要结构。查询接口仍输出原有契约，配置检查或初始化期间不伪造 run 进度。

遥测异常在后端隔离，但每事件原子操作、时钟读取和同步管道写出仍有成本；下游停止读取标准输出时可能阻塞，不能承诺零开销。实测范围与原后端比较见 [F6接续检查点.md](F6接续检查点.md)。不提供实时部分剂量、不提供两轮之间改参数的 F2 会话能力。

## 验证入口

- `scripts/test_live_progress.py`：真实 1/2/4 worker、多 run、零事件、配置失败、worker 故障、最终收尾失败、日志噪声、收到实时消息后强杀。终值逐 run 对账摘要。
- 可选 `--baseline <改前后端> --report <JSON>`：同种子单/双 worker 的排序原始 hits 与事件能量记录逐值比较，并测量交替进程耗时；比较不泛化为全部物理配置的等价证明。
- `gui/smoke_tests/smoke_live_progress.py`：解析、Qt 状态/语言、真实 QProcess 分块与尾流、旧后端、失败、停止/强杀。
- `gui/smoke_tests/smoke_live_progress_backend.py`：GUI runner 连接真实 Geant4，双 run、100% 后最终输出失败、运行中强杀。
- 统一平台注册 `live_progress`、`gui_live_progress`、`gui_live_progress_backend`；整套验收仍核对源码指纹、跟踪门禁和 pass/fail/skip。
