# 输出数据契约（M0-4 工作区候选）

本页依据当前 `OutputManager`、`ScoringManager`、`EdepScorer`、`ParticleHit`、`RunAction` 和 `SimulationManager` 的实际写出行为。它描述数据结构，不证明物理模型或偏置效果正确。`run_summary.txt` 的 `run_summary_schema_version=1` 标记摘要分节结构；工作区 `output_csv_schema_version=3` 标记下述带单位列名的 CSV。旧摘要缺少版本字段时，不能推定它采用新约定。

2026-10-16 有效配置快照候选：最终收尾阶段附加 `effective_config_snapshot_version=1`、`effective_config_snapshot_scope=manager_state_subset`、`effective_config_macro_execution_status`，从 Manager/Context 读取一部分最终值；`effective_config_source_coverage=startup_geometry_source_and_physics_reference` 表示追踪六个启动字段、三个几何字段及 `source_particle`、`source_energy`、`physics_reference`；历史摘要的 `startup_fields_only` 只表示六个字段，`startup_and_geometry_fields` 表示六个启动字段及三个几何字段，读取程序还须兼容 `startup_geometry_and_source_particle`、`startup_geometry_and_source_particle_energy` 旧枚举值。`effective_config_geant4_applied=unknown` 仍不宣称全模块来源或 Geant4 已应用状态。启动时的 `materials_file` 仍表示主配置选用的原始文件；`effective_materials_loaded_file_count` 和从零开始的 `effective_materials_loaded_file_N` 按成功加载顺序记录材料文件（可能重复），路径以摘要路径格式写出。`effective_materials_source_status` 可为 `single_file`、`multiple_files`、`non_file_mutation`、`incomplete_load`、`no_file_loaded` 或 `manager_unavailable`，仅 `single_file` 时 `effective_materials_file` 给出唯一文件，否则为 `unknown`。`non_file_mutation` 包括 macro 中的显式材料定义或清除操作；`incomplete_load` 表示一次已进入材料构建阶段的加载失败，不能保证已建对象已回滚。文件记录不包含已构建 NIST 内置材料的完整来源链，也不意味着某个材料已用于几何。

来源字段覆盖 `output_dir`、`run_name`、`threads`、`seed`、`macro_file`、`check_overlaps`、`geometry_template`、`geometry_config`、`geometry_default_world_material`、`source_particle`、`source_energy`、`physics_reference`，分别采用 `effective_<field>_origin_kind/file/line/section/key`；`kind` 为 `default`、`main_ini`、`cli`、`macro` 或 `runtime_unattributed`。INI 来源保留原始 section/key 和行号；成功执行并经过 Messenger 错误检查的已识别 macro 保留命令名、文件和行号；无对应属性使用 `not_applicable`。CLI 锁定字段不会被 macro 重新归属，无法可靠归属的其他 setter 记为 `runtime_unattributed`。几何字段从主 INI 读取时记录原始 section/key 和行号，成功执行 `/AIHL/geometry/setTemplate`、`/AIHL/geometry/loadConfig`、`/AIHL/geometry/clear`、`/AIHL/geometry/setDefaultWorldMaterial` 后更新对应来源。`/AIHL/geometry/clear` 仅清空 `geometry_config`；摘要追加 `effective_geometry_default_world_material` Manager 当前值。来源不证明 Geant4 已应用，也不包含完整几何对象状态。`source_particle` 从主 INI 的非空 `particle` 记录来源，缺失时从非空 `preset` 记录来源；成功执行 `/AIHL/source/preset`、`/AIHL/source/particle`、`/AIHL/source/reset` 时记载对应命令及来源行号（reset 后当前粒子为空）。另记录 `effective_source_energy_MeV`（SourceManager 当前单能值，以 MeV 表示，0 表示未设置/已 reset）：INI 非空 `[source]/energy` 优先于 `[source]/preset`；成功 batch `/AIHL/source/energy`、`/AIHL/source/preset`、`/AIHL/source/reset` 更新能量来源，`/AIHL/source/particle` 不改变能量来源。这两个值属于 SourceManager 状态，不追踪 Geant4 原生 `/gps/*` 命令的实际影响。这不是全模块 `EffectiveConfig`：其他 Messenger、交互式宏与 Geant4 内核实际生效状态尚未完成审计。

批处理 macro 在 `/run/initialize` 或隐式 `/run/beamOn` 初始化后修改材料的命令会在执行前失败，并保留 macro 文件/行号；交互会话的所有材料生命周期与命令失败传播仍待闭合。该快照是 M0 的部分进展，不能代替可复现的完整 `EffectiveConfig`。

批处理 `/AIHL/output/*` 命令出现 Messenger 内部异常时，即使 Geant4 `ApplyCommand()` 返回 0，后端也会依据独立命令失败计数中断 macro、记录失败命令文件和行号，并以非零退出码尽力写出 `status=failed` 摘要；由于没有非零 Geant4 返回码，摘要使用 `macro_failure_code_available=false`。`/AIHL/output/setDir` 先更新 OutputManager，再更新 context 和来源；底层 setter 拒绝修改时保留原目录及 `effective_output_dir_origin_kind`，不将失败命令写成有效来源。实际后端回归使用测试专用 `G4USIM_TEST_OUTPUT_FAULT=messenger_set_dir` 和 `manager_set_dir` 验证这两个边界。交互会话结束时现会检查材料和输出 Messenger 的命令失败计数：有失败则非零退出，摘要写 `status=failed`、`interactive_command_failure_kind/message`；没有执行 macro 时 `macro_execution_status=not_run`。`--ui --ui-session csh` 可用于命令行回归。此检查在会话结束时进行，不能保证失败命令之后的交互操作立即停止；其他 Geant4 命令的逐条失败传播尚未验证。

`physics_reference` 来源按最终 PhysicsManager reference 名称归属：有非空 `[physics]/reference` 时先使用该 INI 字段；在 reference 模式下还配置非空 `[physics]/em` 时，后者决定 reference 的 EM 变体，来源转为 `em`。成功批处理 `/AIHL/physics/setReferenceList`、`/AIHL/physics/setBaseReferenceList`、`/AIHL/physics/clearReferenceList` 会覆盖来源；`/AIHL/physics/setEM` 仅在 reference 模式下覆盖该字段来源。`effective_physics_reference` 可为空（已退出 reference 模式）；`effective_config_geant4_applied=unknown` 持续有效。读取程序须允许此前四种覆盖范围枚举，不应以当前枚举反推历史摘要字段存在。

## 文件身份与生成条件

交互式 `csh` 对命令不存在使用 `interactive_command_failure_kind=geant4_command_not_found`，对本机已复现的参数类型拒绝使用 `geant4_invalid_parameter`，对参数越界使用 `geant4_parameter_out_of_range`，对 `illegal application state -- command refused` 使用 `geant4_illegal_application_state`。例如在 PreInit 执行 `/run/abort` 时，即使随后执行只读命令，仍须在会话结束后写 `failed` 摘要并非零退出；异常命令之后的其他命令可能已经执行。当前只识别这四类明确诊断，仍不具有每个 Geant4 UI 命令的返回码审计能力。

2026-10-19 交互物理命令守卫：进入 `--ui` 会话后，已注册的 Geant4 physics list 不会随 PhysicsManager 内存字段自动重建。`/AIHL/physics/print`、`listAvailableReferences`、`listAvailableEMReferences` 仍可查询；其余修改型 `/AIHL/physics/*` 命令被 Messenger 拒绝，错误摘要使用 `interactive_command_failure_kind=physics`，若还存在其他交互失败则为 `multiple`，并记入 `interactive_command_failure_message`。已执行的 run 及成功输出保留；会话结束非零退出。物理配置修改需改用新进程中初始化前的 batch macro；原生 Geant4 UI 命令的完整逐条审计仍未完成。

默认启用线程后缀。首个 run 保留兼容文件名 `*_tN.csv`，后续 run 使用 `*_tN_rR.csv`；`N` 是 worker 编号，`R` 是 Geant4 run ID。若线程后缀被显式关闭，后续 run 仍使用 `_rR`。`run_summary.txt` 在最终生命周期写一次，不带线程后缀。不同 run 的 `eventID` 可重复，必须以 `(runID, eventID)` 识别事件；当前 CSV 没有独立的 worker ID 列，需追溯 worker 时应保留源文件名。

| 文件 | 创建条件 | 内容和边界 |
| --- | --- | --- |
| `hits_tN[_rR].csv` | 计分启用、hits 输出启用，且敏感体产生符合过滤条件的 hit | 每个被接受的 step 一行；零沉积 step 默认不写。没有文件可表示没有合格 hit，不等于运行失败。 |
| `event_edep_tN[_rR].csv` | 计分与 event edep 输出均启用，且 worker 完成事件 | 每个完成事件一行；无 hit 的事件也写零值。关闭总计分开关时不应出现此文件。 |
| `hist_edep_raw_tN[_rR].csv`、`hist_edep_weighted_tN[_rR].csv` | 计分与 Edep scorer 启用，且对应直方图开关启用，run 到达写出阶段 | 每个 worker、每个 run 一份；即使零事件也可能只有零计数。超出配置区间的事件进入内存 underflow/overflow，不在 CSV bin 行中，不能把 bin 计数之和无条件当作完成事件数。 |
| `edep_volume_summary_tN[_rR].csv`、`edep_particle_summary_tN[_rR].csv` | 计分与 Edep scorer 启用，且对应分类汇总开关启用，run 到达写出阶段 | 每个 worker、每个 run 一份；无 hit 时可只有表头。分类名称来自 hit 的 volume/particle，未定义名称按 `unknown` 处理。 |
| `run_summary.txt` | 最终收尾阶段，包括 dry-run、无 run 和失败收尾；摘要写入本身失败时可能不存在 | `[Values]` 保存配置计划与实际状态，`[Runs]` 保存每次 run 的计划/完成事件，`[GeneratedFiles]` 保存写出组件显式登记且收尾时仍存在的文件，`[GeneratedFileSchemas]` 逐一保存路径与 schema 标识，另有消息与警告。生成文件清单不表示内容或物理结果已验证。 |

生成文件清单不再通过输出目录递归扫描或比较文件修改时间推断。master 和 worker 的 `OutputManager` 共享带互斥锁的登记表；hits/event CSV 只有显式 `Close()` 成功后登记，Edep 分类汇总也先显式关闭后登记，直方图写出函数成功返回后登记。`GetGeneratedFiles()` 在收尾时只读取该表并过滤已不存在的文件。真实双线程 5000 事件回归已在运行期间注入无关文本文件，验证无关文件不进入清单，实际 worker event CSV 均进入清单。此机制不保证磁盘持久化、文件完整性哈希或防外部篡改；异常退出时未完成关闭的文件可能留在磁盘但不进入清单。

同一共享登记表锁存**首个**输出失败的 `run_id`、`thread_id`、`stage`、`message`；后续失败不覆盖首因。worker 在 hits/event 行写入错误时调用 `AbortRun(true)`，收尾阶段逐项捕获错误并继续尝试关闭 worker CSV，master 在 batch `/run/beamOn` 返回后检查共享失败，避免仅凭 Geant4 命令返回码宣称运行成功；交互模式则在 UI 会话结束后检查。可写摘要时，`[Values]` 的 `output_failure_status` 为 `failed`，并填入四个来源字段，`status=failed`、`program_exit_code` 为非零；无输出失败时状态为 `none`，其余字段为 `not_applicable`。失败的 CSV 不进入 `[GeneratedFiles]`，但成功关闭的其他部分文件仍可能登记。已有双线程真实后端测试通过 `G4USIM_TEST_OUTPUT_FAULT=event_row_t0` 和 `summary_close_t0` 注入 worker 事件写入与分类汇总关闭故障，验证非零退出、失败摘要及 macro 失败位置。这个环境变量是**测试故障注入接口**，正常运行环境不得设置；并不代表真实磁盘满、断连或进程被强制终止时都能成功写出摘要。

主线程最终化还分别捕获 `final_flush`、`final_close` 异常：即使第一个操作失败也会尝试第二个，保留首因，尽力写出包含 `output_failure_*` 的失败摘要，且正常执行路径返回非零退出码。测试专用 `G4USIM_TEST_OUTPUT_FAULT=final_flush_master|final_close_master` 会在真实最终化分支执行相关操作后模拟抛出异常，用于检验错误记录、摘要写出和退出码，**不等同于真实操作系统写入/关闭失败**。若连 `run_summary.txt` 都无法写入，则只能在 stderr 报告摘要失败，不保证摘要存在。

运行启动阶段的 `SetRunId`、`run_id_begin`、`Initialize` 和 `ScoringManager::BeginRun` 现在分别按 `run_begin_set_run_id`、`run_begin_summary`、`run_begin_initialize`、`scoring_begin_run` 登记异常并请求停止 run。切换 run 时 `SetRunId` 仍先关闭前一轮文件，失败首因的 `output_failure_run_id` 指向尝试启动的新 run，错误消息保留底层操作上下文；第一轮已成功登记的数据不会因此被当成第二轮。`Flush` 对两个 CSV writer 独立尝试并保留首个异常。`begin_set_run_id_t0` / `begin_scoring_t0` 是仅用于真实双轮 Geant4 回调测试的人工注入模式；未覆盖真实设备故障和所有线程/进程中断路径。

CSV 首行为列名，逗号分隔并按标准 CSV 引号转义；当前 C++ writer 不强制或标记字符编码，CSV 内容中的跨平台中文名称仍需单独验证。摘要中的已知路径和生成文件路径在写出时转换为 UTF-8；Windows 中文主配置、macro、输出目录已有真实回归，但任意自由文本/诊断的编码仍未闭合。写出数值使用约 12 位有效数字；空字符串不是统一缺失值标记。v3 在能量列名后附 `_MeV`、长度列名后附 `_mm`；权重和方向分量无量纲。直方图 `count` 表示入 bin 的事件计数，而非权重和。尚未开放的通用直方图没有已验证的轴单位，仍使用旧表头并在摘要中标为旧结构或 `unknown`，不得当作已标注 MeV。

## CSV 列

| 文件 | 列名（顺序固定） | 语义 |
| --- | --- | --- |
| hits | `runID,eventID,trackID,parentID,particle,edep_MeV,ndep_MeV,stepLength_mm,x0_mm,y0_mm,z0_mm,x1_mm,y1_mm,z1_mm,px,py,pz,kineticEnergy_MeV,process,volume,weight` | ID 为整数；`p*` 是 pre-step 动量方向分量；`weight` 是 track weight。`process` 可为 `none`，`volume` 可为 `unknown`。v2 的 `LETcalc`/`LETstep` 零值占位列已从 v3 移除，**不得用旧列推断 LET**。 |
| event edep | `runID,eventID,raw_edep_MeV,weighted_edep_MeV` | 每事件敏感 hit 的 `edep` 之和，以及逐 hit 的 `edep × track weight` 之和；不是 Dose。 |
| 原始与加权 Edep 直方图 | `bin,low_edge_MeV,high_edge_MeV,center_MeV,count` | bin 索引为整数；raw 文件按事件原始 Edep 入 bin，weighted 文件按事件加权 Edep 值入 bin，但 `count` 本身每事件加 1，**不是权重和**。 |
| Edep 分类汇总 | `name,raw_edep_MeV,weighted_edep_MeV` | 按 volume 或 particle 名称合计敏感 hit 沉积；加权列逐 hit 乘 track weight。 |

## 合并与兼容

`scripts/merge_outputs.py` 只对同表头的 hits/event CSV 按稳定路径顺序拼接，不合并同名事件或计算统计量；它拒绝空文件、重复路径、列数或表头不一致、已有目标。`tools/mergeHistograms.cc` 对相容 bin 的直方图计算每 bin 的 `sum,mean,stddev,n_files`，输出 `bin_low,bin_high,sum,mean,stddev,n_files`；`stddev` 是输入文件间计数的总体标准差，不是事件统计不确定度。工具兼容旧三列 `bin_low,bin_high,count` 和当前五列原始格式。两种工具都不自动运行，且合并结果不是物理验证。

CSV v1 的 hits/event 文件没有 `runID` 列，多个 run 可能复用同一文件名并覆盖较早数据；不能仅凭旧文件重建所有 run。v2 增加 `runID` 和 `_rR` 分文件，但数值列没有单位且 hits 保留不可用的 LET 占位列。v3 保持 run 文件命名与数据值，给已验证物理量的列名加单位并删去两个 LET 占位列；依赖旧列名或按列位置读取的消费者必须按表头及摘要版本迁移。`merge_outputs.py` 能分别合并同表头 v2 或 v3，拒绝混合版本；`mergeHistograms` 能读 v2、v3 和旧三列直方图，只有全部输入为显式 MeV 的 v3 时才在合并结果边界列保留 `_MeV`，其他组合使用不带单位的兼容表头。当前工作区用真实后端和合并工具回归校验表头、run 分离及两种 worker 输出故障注入；全面字符编码、真实设备故障与物理基准尚未完成，因此 M0-4 仍为部分支持。

写出失败检查已覆盖 CSV 行写入、显式刷新以及关闭时的最终刷新/关闭状态；直方图、分类汇总与摘要写出现在也显式检查最终刷新/关闭，不再只依赖吞异常的析构函数。批处理 macro 的 `/run/beamOn` 之前会检查已知 CSV 目标路径是否被目录占用；首轮与第二轮 `_r1` 冲突回归均在事件启动前失败，生成标记为 `failed` 的摘要及命令位置，第二轮失败时保留首轮已完成事件与文件。交互式 `csh` 的手动 `/run/beamOn` 在 Geant4 `BeginOfRunAction` 的 master/sequential 回调中执行相同目录冲突检查，失败登记 `output_failure_stage=run_begin_validate_targets`、尝试启动的 run ID、零完成事件和非零退出；已有真实双线程首轮与单线程第二轮冲突回归，首轮输出在第二轮拒绝后保留。交互失败发生于 run 开始回调，因此 `run_count` 可以包含已开始但零完成事件的 run，且没有 batch macro 文件/行号。Python 合并工具在注入结果发布失败后不会留下可见的半成品或临时文件。worker 写入和关闭异常传播已有上述两种真实故障注入回归，但尚未模拟后端磁盘满、设备断连、进程中断以及任意 worker/文件组合；目录预检也无法排除检查与创建之间的竞态。不得把上述检查称为完整输出故障闭环。

`[GeneratedFileSchemas]` 使用成对的 `file_<序号>_path`、`file_<序号>_schema`，序号顺序与 `[GeneratedFiles]` 一致。摘要通过实际 CSV 表头识别已知文件的 `hits_csv_v3`、`event_edep_csv_v3`、`histogram1d_csv_v3`、`edep_summary_csv_v3`，同时可识别相应 v2 旧表头；摘要本身为 `run_summary_v1`，空文件、错误表头及其他文件标为 `unknown`。标识说明结构，不表示列值已经通过物理基准。
